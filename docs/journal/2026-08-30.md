# 2026-08-30 — Uploaded fonts, a project file that carries the project, a palette seen through someone else's eyes, and a dozen tests that could not see what they claimed to

## What was done

**A scale can be judged in a font that is not on Google Fonts.** Pick a file, it
renders, it survives a reload, and it never reaches an export. The whole
[uploaded-fonts plan](../roadmap/uploaded-fonts.md) in five stages: the
IndexedDB store, add-and-render, missing files, remove-and-limits, and the
export guard.

The bytes live in IndexedDB under the font entry's id; the project keeps only
the family name and `source: "local"`. That field had been written on every
entry since the model was designed and read by nothing. This is what finally
gave it a job.

Stage 5 was built before stage 4, out of order, because it is the one the others
were already relying on: export emitting names and no faces was true by accident
of what had been written, and three stages of feature were sitting on top of
that.

## What was learned

**A test that cannot see the violation is not a test, however green.** The
removal case passed with the bug present. Deleting a font's metadata and leaving
its file behind kept all twelve store tests green, because every public method
reports a miss once the metadata is gone — which is exactly what an orphaned
copy of someone's licensed font looks like from outside. It had to read the
object store directly. The same thing was true again in the app: nothing on
screen can distinguish "the entry is gone" from "the entry is gone and its bytes
are still there", so those tests read the store too.

**A guard that lists what it covers will rot; one that discovers will not.** The
export guard walks the package's own exports and asserts the set is exactly what
has been classified, so adding a formatter fails until somebody decides whether
it can carry a file. The first version of that filter matched names ending in
`Export` and missed `formatBlueprintPaletteProject`, which serialises a whole
document — the completeness check found a hole in its own author's reasoning
about four minutes after being written.

**"Not loaded" and "not loaded yet" want different things on screen.** Reading
the store is asynchronous, so a boolean reported every present file as missing
until it resolved. No flash was observable — a 28KB file on a fast machine
resolves before paint — which is precisely why it would have shipped. Three
states, and the checking one derived by storing the answer with the question it
answers rather than reset at the top of the effect.

**Two facts conflated into one dependency.** Re-adding a missing file did
nothing: the same file gives the same family name, so the system afterwards was
identical, so nothing re-ran and the font stayed reported as missing while its
bytes sat in the store. The system says _what is named_; a revision counter says
_the stored files changed_. They are different facts and only one of them had
been modelled.

**Prove a guard by adding the thing it exists to stop.** Injecting an
`@font-face` writer into the export — the self-contained-export change someone
would plausibly make in good faith — fails both format cases. Deleting the three
orphan deletions fails exactly three. Neither would have been worth much as an
assertion nobody had ever seen fail.

**Screenshot before writing assertions, again.** The uploaded font rendered under
"is not a Google font, so it is not loaded here", true until that very commit and
then a flat contradiction of the line above it. Every assertion worth writing
first was about whether the font applied, and all of them would have passed.

## Later — a project file that carries the whole project

### What was done

**`blueprint-workspace`.** Exporting a project wrote a `blueprint-palette`
file, which carried no typography at all, so anyone who exported and
re-imported lost their type scale and was never told. The new format carries
both halves. Stage 6 of the
[workspace merge](../roadmap/workspace-project-merge.md), which is now finished.

**One parser, two formats.** `parseBlueprintWorkspace` reads either kind, so
nothing calling it has to know which it was handed. A `blueprint-palette` file
still imports into the palette half — people have those, and a format change is
not a reason to orphan them. A file with one damaged half keeps the other,
because throwing would cost someone the palette that was fine.

Importing is the one place the palette studio writes the other slice. That is
not the slice-ownership rule being broken: an import is someone deliberately
replacing the whole document, rather than a studio persisting a stale copy of a
half it does not own.

### What was learned

**A guard written yesterday caught the first thing added today.**
`formatBlueprintWorkspace` failed the export guard's completeness check on
sight, before it had been given a single test of its own, because that check
discovers the package's formatters rather than listing them. It stayed failing
until the new formatter was classified and asserted to carry no font bytes.
Nothing had to remember to go and update it; it refused to pass until somebody
did.

**Three of the day's bugs were in the tests, and the code was right each time.**

The file was scraped off the export preview, and the code block renders a
language label above the code and line numbers beside it — so the text was never
valid JSON, and the import was correctly refusing it. That read as a broken
import for two rounds. The download is read now, which is the path a person uses
anyway and a better thing to be testing.

The creation screen has a "Project name" field of its own, so asserting on it
after an import passed without any import having happened. An assertion that
cannot fail for the reason you care about is not weaker than a good one, it is
worth nothing.

And storage was read before the effect that writes it had run — the same race
already written down twice on this page, in a third place.

**The pattern under all three: the failure was informative and the first reading
of it was wrong.** Each looked like a defect in the thing being tested. Finding
out otherwise took dumping what the page actually contained rather than
reasoning about what it should contain.

## Later — a plan for colour-vision simulation

### What was done

**A staged plan for [colour-vision simulation](../roadmap/colour-vision-simulation.md).**
The doc had a goal, a system model and a definition of done, and no route
between them. It now has five stages, a section on what the code already
provides, and four settled decisions.

**Machado, Oliveira and Fernandes (2009) over Viénot (1999).** The simpler
linear approximation covers full dichromacy and nothing else; Machado is
parameterised by severity, which is what the anomalous-variants item already
sitting under "later improvements" would need. The signature carries severity
from stage 1 even though the first version only ever passes 1.0, because adding
a parameter later means replacing the transform.

**The report covers typography.** The contrast assessment has taken a font size
and weight since the Thai line-height work, and the workspace has held a type
scale since the merge. A report that names the size its verdict was made at is
worth more than one that does not, and this is the kind of scope that is easier
to include than to add.

### What was learned

**The hardest open question had already been answered, in a component.** "Which
shades does the similarity check compare?" looked like the decision with the
most design in it — every pair is 190 comparisons per deficiency and mostly
noise, one shade per track is a single number that might be the wrong one.
Reading `PalettePreview` showed the normal-vision check already picks four named
pairs of action shades via `shadeAt(track, progress)`. Simulation reuses that
rather than inventing a second notion of which shades matter, and the stage
shrank to moving those pairs into `packages/ui` where they can be tested.

The plan was drafted from the roadmap and the module exports. Reading the
component that consumes them answered a question the plan had escalated.

**Two neighbouring toggles disagreeing is a decision, not a detail.** The
definition of done asks the simulation to survive a refresh. The contrast mode
beside it is component state and does not. Building only what was asked for
would have shipped two switches that look alike and behave differently, so
persisting both is stage 3 rather than a later tidy-up.

**Writing "not from memory" into the plan is the point of the plan.** Plausible
matrices would pass greys-stay-grey, outputs-stay-in-sRGB, and every other
property worth asserting, because those constrain the shape of the transform and
not its coefficients. The stage says the reference values come from the paper,
which is the only test that can tell a correct matrix from a convincing one.

## Later — colour-vision simulation, all five stages

### What was done

**A palette can be looked at through someone else's eyes, and the report says
what that showed.** The whole
[colour-vision plan](../roadmap/colour-vision-simulation.md): the transform,
its invariants, the Vision chip, the warnings, and one accessibility report as
Markdown and JSON.

**The matrices were extracted by script, not typed.** All 33 of Machado,
Oliveira and Fernandes (2009) parsed out of the authors' supplementary table
into `machado2009.ts`, so no digit passed through anybody's memory. Three
checks that the extraction stayed aligned: severity 0.0 is exactly the
identity, every row sums to 1, and reproducing colour-science's published
doctest from our table reaches their numbers to nine decimal places.

**No LMS space was needed.** The plan called that the one piece of genuinely
new colour maths. The published matrices fold the cone round trip in and act on
linear RGB directly, so the only conversion required was the sRGB transfer
function — which already existed as two private copies and is now exported
once.

**The Vision chip is its own on/off.** No separate switch, so the list holds
the four deficiencies and not a fifth "normal vision" entry that would give two
ways to say the same thing and let them disagree. The chosen mode survives
being switched off.

**The report carries the type scale.** Each role measured at the size the scale
gives it, against the body-text pair, with that pair named. The same two
colours pass at a heading and fail at a caption, which is the whole reason a
size-aware verdict is worth having.

### What was learned

**The cross-check found a bug in the library it was checking against.**
colour-science publishes a doctest for protanomaly at severity 0.15 — a value
between two tabulated matrices, so it tests extraction and interpolation at
once. Ours disagreed. Their `searchsorted` lookup picks the bracket _above_ the
requested severity and then walks backwards into it, so 0.15 is extrapolated
from the 0.2 and 0.3 matrices rather than interpolated between 0.1 and 0.2.
Reproducing that arithmetic from our table hits their numbers exactly, which
confirmed the extraction and identified the defect in the same step. The test
says why we do it differently, because otherwise somebody will "fix" it to
match the better-known library.

**Two properties the plan asserted were false, and the code was right both
times.** Red and green collapse in _hue_, not in overall difference —
protanopia costs red most of its luminance, so a large OKLab distance survives
and an assertion on it reads as a broken transform. And simulating twice is not
simulating once: that holds for the projection models, but Machado shifts cone
sensitivities and a second pass shifts again, by up to 44 levels per channel.
Both are asserted in the negative now.

**A dozen examples wearing an invariant's name.** Every property started life
checked over twelve hand-picked colours. Moving them onto a 4096-colour grid
through the cube turned up two more things the plan would have got wrong:
severity does not move a colour monotonically — under tritanopia `#00ffdd` is
furthest from its original near 0.2 and comes back by 0.5 — and the transform
is smooth in severity except against the black wall, where the sRGB encoding is
steep and a channel pinned at zero moves 25 levels per 0.01.

**A mutation that does not apply looks exactly like one that survives.** Two
survived a pass and neither was a weak test: Prettier had rewrapped the matrix
arrays so one search string never matched, and the other replaced a formula
quoted in a _comment_ rather than the code, because the comment named both
forms it was contrasting. Mutations now run through a helper that fails loudly
when the edit does not land, and it caught a third silent no-op immediately.

**The clamp test was testing `rgbToHex`.** A range check on the hex output can
never fail, because `rgbToHex` clamps on its way out. It passed with the clamp
removed from the transform until it was pointed at the unrounded channels.

**Two rounds lost to a 200ms transition.** A swatch read straight after a mode
change returns the previous colour, which looks exactly like a transform that
did not apply. The first fix — waiting for React to re-render — did not help,
because the lag was the CSS transition, not the render. Before concluding that,
the change was stashed and the original component run against the same
assertion, which ruled out a pre-existing bug that was about to be reported and
does not exist. The helper polls until the computed value matches the inline
one, which is the definitive "the transition has finished" condition rather
than a sleep.

**The guard written for fonts caught the first two formatters added today.**
Both report formatters failed the export guard's completeness check on sight,
before either had a test of its own. The font family was then added to the
typography rows specifically so the case is real: the report names families and
is asserted to carry no bytes, in both formats.

**Reaching for CSS before reading the component's props.** The chip's icon
stacked above its label, and two rounds of flex rules did not fix it — the
Button wraps children in a `min-w-0` span. It has a `leftIcon` prop, which was
there the whole time.

**The feature's first real output was about the default palette.** Run against
the seeded project, all four semantic pairs collapse under at least one
deficiency and three under deuteranopia. That is the thing working on real data
rather than a contrived fixture, and it says the shipped default leans on hue
to separate its status colours.
