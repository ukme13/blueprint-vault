# 2026-09-06 — A type scale documented, and eight roles stored at one size

Stage 3 of the foundations plan, typography only. One page rendered from the
reference workspace's type system, with written guidance, in light and dark.

## What was done

**The rows live in the package.** `typography/role-rows.ts`, beside
`color/token-rows.ts` and for the same reason: the studio's role editor and
this page describe one system, and each would otherwise decide for itself what
a row is. Which size a role resolves to, what element it renders as, which
variables it exports under — three rules, three chances to drift.

**The variable names come from the export's own function.** `typeTokenId` was
private to `system-export.ts`; it is exported now, and the rows call it. The
unit test checks the rows against the export's actual output rather than
against a second list, and the case that separates them is a role called "Body
Large": a local `toLowerCase` gets the hyphen wrong and a developer copies a
variable that resolves to nothing.

**The preview templates moved into `@blueprint/ui`.** The README's rule is that
a second application needs it, and this page does. Their three layout rules did
not come with them — a package shipping a stylesheet would be deciding what a
gap is for every app that renders one — so the classes travel as a prop, which
is the arrangement Button already has. The studio passes the same module
classes and renders identically: 224 e2e passed, the same as before, including
the two tests that switch templates and languages.

**The page is the colour pages' shape.** Guidance, the scale, the roles, the
specimens, then the article. A developer arriving for a variable name finds the
table without reading the prose; a designer arriving to judge the scale reaches
the specimens having been told what a role is.

## What the page found

**Every role in the reference workspace is stored at 16px.** Eight roles, eight
different step offsets, one stored size. The studio resolves the offset against
the ramp on read and never writes the result back, so the stored number has
been meaningless since the model merge and nothing had ever needed to notice. A
page printing `role.desktop.fontSizePx` would have shown eight roles at one
size and called it a scale.

**The article template asks for roles a default workspace does not have.** It
wants `label`, `title`, `heading`, `body` and `display`; a default system has
`display-1`, `h1`–`h6` and `body`. Four of the five fall through to body, so
the article renders its kicker, its standfirst, its byline and both section
headings at 16px. The fallback is doing exactly what it was built to do, and
what it is hiding is that the templates and the model have been out of step
since the merge. Left alone: the same fallback runs in the studio, and changing
it is a studio change.

**The plan named five default groups and there are three.** Display, heading,
body, label and caption is the group table from the typography rework, not what
`defaultSystem` builds. The guidance covers the three that exist and a test
checks its names against the seed system, so the prose cannot quietly describe
an intention again.

## Lessons

**Astryx's own guidance can be unfollowable, and the failure was the good
kind.** "Set an explicit width on every column" lives in the Table's
data-driven mode, whose `columns` array carries a `renderCell` function — and a
function cannot cross into a client component from a server one. It failed the
build with the offending prop printed, rather than rendering something subtly
wrong. Composed rows are the only option from a server component, and there the
cell sets `overflow-x: hidden` on an auto-layout table: three variable names
were clipped at 1280px and eleven at 900px, silently, with no scrollbar to
suggest anything was missing.

Two wrappers were tried before measuring properly, and neither moved the
number. Walking the element chain and reading `overflowX` at each level took
one run and gave the answer: it is the cell, not the table and not the page.
The names wrap now. A wrapped name is ugly and complete; a clipped one is tidy
and wrong, and it is the tidy one somebody copies.

**Rendering a role as its real element puts it in the page's outline.** The
plan asked for it and the plan was right — an `h2` role has to be an `h2` or
the page is describing something it is not showing. It also gives a reader
navigating by heading eight top-level headings, six of them the same six words.
The tag stays and `aria-level` moves the announced level, which is the
distinction that was wanted all along: a sample of a heading, not a heading of
this document. The cost was not in the plan and was created by the plan's own
instruction.

**A directive is a property of a module, not of a component.** `"use client"`
at the top of the preview templates made the whole file a client boundary, so a
server component could not call a plain function exported beside them. They are
constants and pure JSX; the directive was only ever there because the file
lived in the studio's tree. Moving a component between applications means
asking which of its annotations were about the component and which were about
where it happened to live.

**Nothing on this page has ever rendered a Google font or an uploaded one.**
Both fonts in the reference workspace are the same system family, so the two
paths that matter most to a client are written, unit-tested, and unexercised on
the page itself. That is worth fixing in the fixture before stage 5 hands one
to somebody.

# Later — a client's file said every role was 16px

Four findings from the typography page, closed. One of them was not the finding
it looked like.

## The export was writing the wrong number

The page's own note said the reference workspace stores every role at 16px and
the studio resolves on read. True, and incomplete: the CSS export read that
stored field directly. So the generated file — the artefact a client installs,
the whole point of stage 1 — declared `--font-h1-size`, `--font-h2-size` and
`--font-display-size` all at 16px, beside a correct `--font-size-8: 62px`. The
line heights were wrong with them, because a line height is computed from the
size it sits on.

Nothing on any screen showed it. The studio resolves the step offset before it
renders and so does the documentation page, so the scale was right everywhere a
person looks and wrong in the one place nobody does.

**The field could not be deleted, which is what the brief asked for.** It looks
dead — every value in a seeded system is inert — but it is the store for a
hand-set size. The studio's size input writes there and sets `stepOffset: null`,
and an unlinked role has no step to resolve against. Deleting it would have
deleted the Custom size control and silently reset every role somebody had
tuned by hand. It is documented as what it is instead, and a guard now holds
the row builder and the exported file to the same number for every role.

Fixing it surfaced a second one immediately. `resolveSystemRoles` copied the
desktop size into both viewports, which was harmless in the studio because the
studio only ever renders desktop, and became a regression the moment the export
called it: a system authored at two sizes lost its mobile one. A pre-existing
export test caught it on the first run.

## The slot rules had to be different from the rules

The templates ask for six role names a merged-model workspace does not have, so
five of six slots fell to body. The fix is a resolver in the package, shared by
the studio and the documentation, and an exact id always wins.

The rules underneath were specified as one role per group, and one role per
group does not work. A heading slot taking the heading group's first role gets
`h1`, which on a default system is 62px — identical to `display-1`. The hero,
the standfirst and every section heading would have come out the same size, so
the article would have been fixed into a different kind of broken. A standfirst
is a subordinate title; a section heading sits under it. They take the second
and third heading roles, and the article now runs 62 / 48 / 40 / 16 where it
ran 62 / 16.

Doing that split one function into two. A template asks which role should draw
its heading slot; the specimen list already has a role and asks what it looks
like. One function had been answering both, which is precisely how the slot
chain came to answer for a concrete role.

## Lessons

**A correct screen is not evidence of a correct file.** Two readers of the same
data, both resolving before they render, agreed with each other and disagreed
with the export — and the export is the only one of the three anybody outside
this repository ever sees. The guard that would have caught it is not a better
test of either reader; it is a test that the two readers agree, which is a
different assertion and the one worth having.

**"Remove the dead field" was the right diagnosis of the wrong thing.** The
field was carrying a stale value _and_ holding a feature. Both were true, and
acting on the first without checking the second would have been a silent data
loss shipped as a cleanup. The check took one grep of the size input.

**A measurement can be right and still not be a defect.** Seven spans on the
colour page report as clipped — 1px wide, holding 50px of text — and should
stay exactly as they are. `sr-only` is indistinguishable from a cut-off name by
the only measurement that finds cut-off names. The tool cannot tell you which
one you are looking at; only reading the element does.

# Later again — three pages that mostly did not need a row builder

Stage 3 finished: spacing, radius and elevation, one page each, the same shape
as the typography page beside them.

## What was done

**A row builder small enough to look unnecessary.** Its colour and typography
siblings exist because two readers of one system would otherwise each decide
what a row is. Here they would not — `resolveSpacing`, `resolveRadius` and
`resolveElevation` are already what the export calls to write the file, so a
page calling the same functions cannot print a variable the file lacks.
`scale-rows.ts` carries two things and no more: elevation paired across its two
modes, and the shade a shadow was drawn from, which the resolution otherwise
consumes on the way to an `rgba`.

**Three pages, three specimens.** Spacing draws each step as a bar, because a
column of numbers says 24 is twice 12 and a column of bars says what twice
looks like. Radius draws each corner on a bordered surface, since a corner is
only visible where two edges meet. Elevation draws every level four times: on a
light ground and a dark one, in whichever mode the reader is in.

## What the pages found

**Elevation's grounds cannot be semantic utilities, and that is not a
shortcoming of the page.** The whole claim it makes is that a shadow's colour
does not change between modes and its strength does — which needs a light
ground and a dark one visible at once. A semantic utility resolves to whichever
mode the reader is in, so `bg-surface-base` would draw the same ground twice
and prove nothing. The playground's editor solves this with
`--color-neutral-50` and `--color-neutral-900`, which is a primitive and
forbidden here. So the grounds are `surface.base` and `surface.raised` resolved
per mode and passed in as values, the way `Swatch` already takes a hex: a role
named, resolved from the workspace, never typed.

**The scale roadmap got nothing wrong.** That is worth recording precisely
because the last two branches found the opposite. It opens by correcting its
own earlier draft — "it was going to be spacing is the same maths as type,
reuse `generateTypeSteps`; reading the tokens first showed that is wrong" — and
that correction is the substance of the spacing page's first section. A ratio
of 1.25 over a 4px base gives 6.25px steps that look principled and cannot be
used. The plan had already been through the mistake the page would otherwise
have documented.

**A token that knows what it is for beats a paragraph that knows it.** Every
radius token carries its own description, written when the token was defined,
so that page's table has a "what it is for" column filled from the workspace.
Spacing steps and type roles have no equivalent, which is exactly why their
pages carry more prose. The difference is visible in the page length.

## Lessons

**A convention is only worth having if it is enforced against its own
awkward cases.** The guidance names a counter-example — there is no radius-2 —
and the test that every backticked token exists would have failed on it, along
with rgba, var() and box-shadow. The temptation is an ignore list. The better
answer was to decide what a backtick means: it means "this exists". A
counter-example and a piece of CSS syntax are neither, so they lose their
backticks, and the test goes back to stating something obvious rather than
guessing at intent.

**Picking the value a test asserts on is part of writing the test.** The
spacing test changes the base unit from 4 to 6 and checks the page moved. The
first version asserted on 24px, which passed before the edit as well as after —
step 6 at a base of 4 is also 24. A test that cannot fail is worse than no test
because it reads as coverage. 9px is step 1.5 at a base of 6 and cannot be
produced by the seeded scale at all, which is the property the assertion
actually needed.

# Later still — an allowlist that stayed empty

Stage 4: the scanner that has held the playground's preview page to "no
hardcoded value" now holds every page in the documentation, and the two pages
that predate the token layers were swept onto it.

## What the numbers were

Pointed at `apps/docs` for the first time, with the generated export, the test
files and the content modules out of scope: **68 findings across six files**.
The Button page had 26 and the home page's stylesheet 31, which is what a plan
predicts when it says "they predate the layer". The other four files had one or
two each, all radius utilities and a pair of colour fallbacks.

After the sweep: **zero**, with an allowlist holding nothing.

## The allowlist did not need an entry

Two were expected — the elevation page's grounds and the `Swatch` — and neither
turned out to need one. The reason is the same for both, and it is a fact about
what a scanner can see: a value that arrives as data is invisible to something
that reads text. `Swatch` takes a hex as a prop. The elevation grounds are
`surface.base` and `surface.raised` resolved through `resolvedRoleReference`.

The only literal either file held was a `#ffffff` fallback for a workspace with
no such role — and that is not a value the scanner should have permitted, it is
a value that should not have been there. A white rectangle would have been the
page inventing a colour the workspace never gave it. It draws nothing now,
which is the honest picture of a workspace with no surface roles.

## What the check had to learn

**That the two apps genuinely differ.** The scale plan is right that `p-4`
reaches a measurement without ever writing px — in the studio, whose
`theme.css` declares colour and nothing else. The documentation installs a
generated `@theme` built from the workspace's own spacing and radius scales, so
`p-4` there resolves to `--spacing-4` and `rounded-container` to
`--radius-container`. Flagging those would have driven these pages into inline
styles to satisfy a check, which is worse than what the check prevents. It
takes the token lists now, so `gap-2.5` still fails — 2.5 is not a step this
scale has — and the mechanism survives one level in.

**That a size is not a distance.** The Tailwind half had always ignored `w-56`
with a written reason. The CSS half flagged every length, which nobody noticed
until it met a page with a content column.

**That an identifier is not a utility.** It reported a local `const rounded =`
and `fontFamily: row.fontStack`. Tailwind patterns look only inside quoted
spans now.

## Lessons

**A check that reports a variable name is a check somebody switches off.** That
is the failure mode this whole stage exists to prevent, and the first run
produced two of them. The value of a scanner is not how much it finds; it is
whether the person reading the output believes it. Every false positive spends
that down, and the fix is always narrower than the temptation, which is to
allowlist the file and move on.

**"Point it at a second root" is never only that.** The scanner already took a
directory. Making it useful against a second application meant a skip list, two
token lists, a size exemption, a quoted-span rule, one broken regex and a
separate entry point — and every one of those came from a real finding rather
than from designing ahead. The stage landed after the pages for exactly this
reason, and the plan was right to put it there.

**A build-time tool is a different product from a component library.**
Re-exporting the scanner from the package root pulled `node:fs` into the
browser bundle and the playground stopped compiling. The failure was immediate
and unmistakable, which is the good kind — but it is worth noticing that the
entry point of a shared package is an API surface, and adding to it is a
decision rather than a convenience.

**The pages could not name five things.** Four levels of grey text against two
foreground roles; no type role under 16px, so an eyebrow and a card title reach
for step tokens; no size family for a content column; no gradient; and no
spacing step at 80px. All are written into the stage 4 notes rather than
worked around. That is the roadmap's own rule — a page argues the vocabulary
into shape — running for the first time on a page nobody designed the
vocabulary for.

# Later again — two roles, argued for by five uses

`label` and `caption` join the default type system. They were asked for at
roughly 14px and 12px and landed at 12 and 11, which is the more interesting
half of the story.

## Why now, and not before

The rule for adding a token is that a page argues for it, and five did: the
article template's kicker and byline, and the documentation home page's
eyebrow, badge and card action. All five had been naming a bare step token —
`--font-size-0` and `--font-size-1` — because nothing under body had a name,
and the typography guidance already said out loud that reaching for a step is a
sign a role is missing. One page wanting something is not an argument; five
uses across two products is.

## 14px does not exist

Two steps below base is 10.24 before rounding and the floor clamps it to 11.
One step below is 12.80, rounding to 12. Base is 16. So the small end of a 1.25
ramp is 11, 12, 16 with nothing in between, and the two roles took the two
steps there are.

Hand-setting 14 would have hit the number and broken the thing a default role
is for. A hand-set size unlinks a role from the ramp, so changing the base or
the ratio afterwards would move every other role and leave these two behind at
14px — which is exactly the failure the `stepOffset` model exists to prevent.

## They could not go in the body group

The brief said the body group and the model would not have it. Every group is
reindexed by position on read — that is what repairs a project an earlier
release left holding both `body` and `body-1` — so putting two roles in the
body group renamed all three. `body` became `body-1`, the new ones `body-2` and
`body-3`, and `--font-body-size` disappeared from a file that clients already
install. The regenerated export showed it in one line.

A group of one takes the group's own id, which is the only shape in this model
that keeps a role called `label` called `label`. It is what `display` already
does, and on the Groups tab it reads correctly: these are named roles rather
than an indexed family.

## The migration had been waiting for them

`legacyGroups` has added `label` and `caption` groups since the merge, because a
pre-merge project has both roles. With the defaults now carrying them that
produced two groups with the same id — the identical fault `display` had, with
the identical comment sitting above it. `legacyGroups` is `defaultGroups` now.

The two shapes converged rather than one copying the other. The pre-merge model
named these roles years before the merged one did, and the pages that argued
them back had never seen it.

## Lessons

**A brief can be right about the need and wrong about the shape.** "In the body
group, at roughly 14px and 12px" was three instructions and the model refused
two of them — 14px is not on the ramp, and the body group renames what it
holds. The need was real and the five consumers were real. Checking the shape
against the model before implementing it cost one regenerated file and would
have cost a broken token in a client's stylesheet.

**The reindexing rule is invisible until you add a role.** It has been there
since the merge, doing something useful, and nothing about reading the model
suggests that adding a second role to a group renames the first. The export was
what said so, which is an argument for regenerating early rather than at the
end.

**A page that needs no edit is the claim being tested.** Two groups and two
rows appeared on `/foundations/typography` with their guidance above them and
their six variables beside them, from a workspace file and a content module
keyed by group id. Stage 2 and stage 3 asserted that by rendering the same
workspace twice with one value changed. This is the first time the data itself
grew and the page simply followed.

# Later still — a folder a client keeps

Stage 5. The export dialog gains a Handover (.zip), `pnpm handover` builds the
foundation pages against any workspace file, and the plan's open question is
settled by the shape of the thing rather than by argument.

## The split, and what it decides

Everything in `buildHandoverFiles` is a pure function of the project —
stylesheets, the workspace, the accessibility report, a README — so a browser
can make all of it and the export dialog does. The foundation pages are a Next
build, which a browser cannot run, so `pnpm handover` makes those and zips both
halves together.

That is the answer to "should the docs render a workspace dropped in at
runtime". Build-time with a parameter: `BLUEPRINT_WORKSPACE` names the file,
both `lib/workspace.ts` and the stylesheet generator read it, and one build
documents any client's system. Runtime would make the documentation a tool;
build-time makes it a deliverable, a folder somebody keeps that needs nothing
running. A deliverable is what this plan was for.

## Choosing a zip library

fflate 0.8.3 against jszip 3.10.1, both checked with `npm view` before either
was installed. fflate is MIT with **zero dependencies**, last touched July 2026. jszip is dual MIT/GPL, pulls **four** runtime dependencies — one of them
`readable-stream`, a Node polyfill that would ship to a browser bundle — and
its last release is August 2022. Both do the job; only one of them is a single
import with nothing behind it.

## Making a static export open from a folder

Next has no option for this, and it is worth writing down why rather than
which. `assetPrefix` is one string for every page, and a page two directories
down needs a different prefix from the one at the top. So `trailingSlash` makes
every route `dir/index.html` — which gives each file a predictable depth — and
the script rewrites `href`, `src` and `url(` per file afterwards, counting
slashes. Measured on the output: no absolute reference survives, and
`foundations/colour/index.html` asks for `../../_next/…`.

## Two things the checks found

**The first real download shipped an empty file.** `designSystemFiles` returns
a fixed-shape record, so a workspace with no type scale gets `""` for
`blueprint-typography.css`. The archive carried seven good files and a
zero-byte stylesheet, listed in the README as though it worked. Found by
downloading an archive in a Playwright test and unzipping it — not by reading
the code — and only because the studio's own e2e fixture happens to be
palette-only. An empty file is left out now, and its README line goes with it,
which comes free from generating the README out of the list.

**An expectation guessed from the model was wrong about the page.** The
verification script first asserted 72 semantic rows and found 116, because the
semantic page carries the contrast table as well as the role tables. Both
counts are derived from the archived workspace now, through the same
`semanticRowGroups` and `typeRoleRowGroups` the pages render by.

## Proved twice, from disk

The reference archive unzips into a temporary folder and every page renders
over `file://` with no failed request that is not a `file:` URL, in both modes:
72 semantic roles, 10 type role rows. Then a second workspace — the same
fixture with a green primary instead of the purple one — through the same
command: its colour page shows `#0B7A3D` and does not show `#7646AB`. That last
half is the assertion worth having. A build that ignored the parameter would
pass every count above it.

## Lessons

**"Can a browser do this?" is a better seam than "should this be a script?"**
The archive divides at exactly the line where the work stops being a pure
function, and everything else follows: what the dialog offers, what the script
adds, and which of the two the open question was really about. A seam chosen
for a reason survives the next feature; one chosen for convenience gets
re-argued.

**Guard what was written, not what was meant.** `unexpectedHandoverPaths` takes
the real directory listing rather than a replay of the script's intentions.
Checking the intentions would have proved only that the script agrees with
itself, and the thing worth catching — a file copied in by hand, or left behind
by an earlier run — is precisely the file the script never mentions.

**A README generated from the file list cannot forget one.** It is four lines
of code and it made two separate mistakes impossible: a file with no
description throws at build time, and a file dropped from the archive takes its
description with it. Prose kept beside data goes stale; prose generated from
data cannot.

# Last — the plan closes, and one item closes differently

Stage 6: the documentation gets its own Playwright project and two CI jobs. The
foundations plan is done, and walking its definition of done turned up one item
that is met differently from how it was written.

## What the browser found that the render tests could not

The unit tests render each table twice with a value changed. That proves the
component is a template; it cannot see a stylesheet that did not ship, a client
component that throws on hydration, or a mode attribute nothing applies. The
first run of the browser suite found three things of that kind at once.

**With nothing stored, the docs open dark.** The shared colour-mode hook falls
back to dark and then persists it, so clearing the key is not the system state
— it is a reader who has not chosen, and they get dark whatever their machine
prefers. Worth knowing; not this branch's to change.

**An init script runs on every navigation.** Seeding the mode without a guard
made a test about persistence measure the fixture rather than the app — it
re-seeded on the reload it was meant to survive.

**`aria-level` on a native heading does nothing.** This is the one that matters,
because I added it in stage 3 with a comment explaining why it was right.
Chrome reports `heading "Build a stable type scale" [level=1]` for an `<h1>`
carrying both `role="heading"` and `aria-level="4"`. The native tag's implicit
level wins. The demotion never worked, and the comment above it had been
claiming otherwise for two branches.

It is gone now. The page has three level-one headings and the reason sits where
the code is: the plan asks for each role rendered as its real element, the
table says `<h1>`, and the specimen has to be one. A template's own heading
level did move — `ArticleTemplate` takes a `headingLevel` now, so the studio
keeps its h1 and the documentation puts the same article at level three.

## The item that closed differently

The definition of done said the export dialog produces an archive with "the
three formats, the workspace, the report and the static foundation pages". It
produces everything but the pages. A browser cannot run a Next build, so
`pnpm handover` makes those and the dialog offers the other eight files. The
split is better than the line — it is what let the same command document any
client's workspace — but it is not what the line says, so it is marked ⚠️ and
explained rather than ticked.

## Lessons

**A test can only check what it can see from outside.** The strongest thing in
this suite is that its expectations are read from the workspace JSON and the
arithmetic is done in the test. An assertion computed with `semanticRowGroups`
would agree with a page rendered by `semanticRowGroups` whatever either of them
did. Reading the file and multiplying says something the page cannot make true
by itself.

**A fix that cannot be observed is worse than no fix.** `aria-level` looked
correct, was standards-shaped, had a paragraph of reasoning above it, and did
nothing at all. Nothing in two branches of review caught it, because reviewing
it meant agreeing with the reasoning. One `ariaSnapshot()` call settled it. The
lesson is not "test more"; it is that a claim about what a browser computes
should be checked against the browser, and it takes one line.

**Walking a definition of done is not the same as ticking it.** Five of six
items were met as written. The sixth was met better and differently, and the
temptation to call that "met" is exactly why the exercise is worth doing item
by item with the test names in hand.

# Alpha in the semantic model

Stage 1 of `docs/roadmap/semantic-table-editor.md`, on `feat/semantic-alpha-model`.
A semantic reference can now carry a transparency, and everything that measures
or exports one knows what to do with it. No UI: nothing sets an alpha yet.

## The export syntax was decided by data, and the data said no

The plan recommended relative colour syntax —
`oklch(from var(--color-neutral-950) l c h / 12%)` — and asked for it to be
checked against the browser floor before stage 1 started. That check overturned
the recommendation.

This workspace declares no `browserslist`, so its floor is Astryx's.
`astryx docs browser-support` refuses to state one number; it defines tiers and
says it officially supports Tier 1 and Tier 2, which makes Tier 2 the floor:
Chrome 114, Edge 114, Safari 17, Firefox 125. MDN's compatibility data, fetched
from the BCD API rather than recalled, puts relative Oklch colours at Chrome
122, Firefox 128 and Safari 18 — outside the floor on all three engines, Safari
by a whole major. `color-mix()` is inside it everywhere: Chrome 111, Firefox
113, Safari 16.2.

The recommendation's objection to `color-mix` was that it "mixes toward
transparent through a colour space the client did not choose". That does not
survive measurement. In Chromium 151,
`color-mix(in oklab, rgb(234 88 12) 40%, transparent)` computes to
`oklab(0.646079 0.146426 0.127797 / 0.4)` — the colour's own coordinates, with
the alpha applied and nothing else touched. Mixing with `transparent`
premultiplies, so the interpolation space decides how the value is written and
not what colour comes out. The objection was to a cost that is not paid.

## The one thing worth measuring twice

`composite(fg, surface)` had three plausible colour spaces and they disagree
loudly: 50% black on white is `#808080` in encoded sRGB, `#bcbcbc` in
linear-light, and about `#777777` interpolated in OKLab. The palette is
generated in OKLCH and its similarity metric runs in OKLab, which makes OKLab
the tempting answer.

It is the wrong one. Compositing is not interpolation — it is what the
compositor does to two painted layers, and the compositor works on the encoded
values. Measured rather than argued: a canvas in the default `srgb` colour
space, filled white and covered with `rgba(0,0,0,0.5)`, reads back
`127,127,127`. A report that said `#bcbcbc` would be describing a page no
browser renders.

## Version 6 is the first bump that is not a missing slice

Every earlier version of the workspace file differed by lacking something that
gets filled on read. A version 5 file has no alpha anywhere and absent already
means opaque, so it needs nothing — it reads back byte for byte.

The number moved for the other direction. A build that knows only version 5,
handed a file with `alpha: 0.12` in it, reads the `trackId` and the `weight`,
ignores the field it has never heard of, and hands back a solid divider. Nothing
warns; the system is just quietly different. Refusing the file is the honest
failure, and only an unrecognised version number can make it refuse.

## Two bugs the field found on its way in

**The editor's badge was a ternary.** `missing === "track" ? "track gone" :
"weight gone"` — so the moment `SemanticMiss` gained `"alpha"`, an out-of-range
transparency was reported correctly by the resolver and displayed as "weight
gone". It is a `Record<SemanticMiss, string>` now, which makes the next one a
type error rather than a wrong label.

**Repointing dropped the alpha.** The editor rebuilt the reference from its two
selectors, so changing a shade on a transparent token would have silently made
it solid. There is no way to set an alpha yet, so nobody could have hit it —
which is exactly why it was worth fixing on the day the field arrived rather
than on the day somebody could.

## Lessons

**A recommendation with a stated check is a question, not an answer.** The plan
said "check relative colour syntax against the floor" and recommended it in the
same breath. Doing the check properly meant being willing to come back with the
other option, and the evidence — three engines, three version numbers, one
floor — is now in the plan so nobody has to take the conclusion on trust.

**"The space the palette uses" is not one space.** Contrast is measured through
linear-light luminance, similarity through OKLab, and both take sRGB hex as
their input. A brief that names "the space" has to be resolved by asking what
the number is _for_, and the answer here was: to agree with the screen.

**Prove the absence, not just the presence.** The claim that no generated file
moves is the one a reader most wants and least believes, so every formatter has
an explicit opaque branch that emits the old characters, a test asserting only
the transparent line differs, and a regenerated `apps/docs/app/blueprint/` with
an empty diff behind it.

# Selection operations, and what the seed set turned out to be

Stage 2 of `docs/roadmap/semantic-table-editor.md`, on
`feat/semantic-selection-ops`. Five pure functions in `packages/ui/src/color`,
one answer shape between them, and no component wired to any of it.

## The measurement that changed the shape of stage 4

`usedBy(id)` answers "what reads this role by name". I wrote it expecting a
handful of load-bearing roles in a designer's vocabulary of seventy-two, put a
test in asserting fewer than half, and measured **seventy of seventy-two**.

That is not a fault in the rule. It is what the seed set is. Nobody designed
seventy-two names and then found consumers for them — the set grew out of its
consumers, one role at a time: seven button tones of eight roles each,
thirty-four names the Astryx bridge feeds into Astryx's own tokens, fifteen the
palette preview measures. A role nothing reads is the exception, and there are
exactly two: `border.subtle` and `border.muted`, seeded as vocabulary rather
than for a caller.

This matters more for the table than for the model. The `usedBy` badge is not
an edge case somebody meets occasionally; it is what almost every row will
show. A rule that said "you cannot delete this" would be a spreadsheet where
nothing can be deleted, which is a wall with a tooltip. Naming the consumers in
plain words, and offering the repoint that is always available instead, is the
whole difference.

The test now holds the exact set of two rather than a count, so a role gaining
or losing a consumer is a decision somebody makes in that file rather than a
number quietly drifting.

## Declaring a name is not reading one

The obvious way to build the consumer list would have counted `theme.css`,
which is listed in the plan as a consumer. It declares all seventy-two roles so
the studio's chrome has them whatever a workspace holds — and counting those
would have made every seeded role undeletable and the feature pointless.

It reaches for exactly two through `var()`: `action.primary-active` and
`surface.raised`. Those are the ones that break if the role goes. The other 233
declarations are the studio supplying names, not depending on them.

## A browser bundle cannot read a stylesheet

Three of the five consumers are computable — the Button tones parse out of
`BUTTON_TONES`, the preview's roles and the pair rule are already exported
lists and rules. Two are CSS files, and `usedBy` ships to a browser where
`node:fs` does not exist. So the bridge's thirty-four names and the chrome's
two are constants, held to their files by a test that reads the same files the
bridge guard reads and fails with the exact list to paste.

That is a copy, and a copy is only as good as the thing that catches it
drifting. It is the same arrangement the docs export guard uses, and it is the
honest trade: the alternative is a subpath export nothing in the browser can
import, which is what the token scanner had to become for the same reason.

## Version 7, and the stronger case of the two

Stage 1 bumped to 6 for alpha. Stage 2 bumps to 7 for `removedSeedRoles`, and
the argument is the same one twice — but this is the worse failure. A
version-6 reader handed an alpha it does not know drops it and changes a
colour. A version-6 reader handed a removed-seed list drops it, finds the role
missing from the layer, and puts it back: it silently reverses an edit somebody
made, in the one direction the reader was built to be helpful in.

Both read doors were wired in the same commit, because the semantic top-up
itself shipped with only one of them once and the same document gave two
answers depending on which way it came in.

## What is reconciled and what is not

An id coming _back_ is inferred from the layer: a duplicate renamed onto it, a
token added by hand and an imported file that has it all look identical from
there, and all three are somebody changing their mind.

An id _leaving_ is not inferred, and that took a moment's thought. "A seed role
is no longer in the layer, so it was deleted" is tidier and wrong on one path:
an import replaces the layer wholesale, and every seed role the incoming
document happens not to have would be recorded as something this user threw
away. So a deletion says so explicitly.

## Lessons

**Write the assumption down as a test, then measure it.** "Most of the seed set
is free to delete" was a belief I could easily have carried into stage 4 as a
design. Encoding it as `toBeLessThan(tokens.length / 2)` and watching it fail at
70 cost one test run and changed what the editor has to be.

**A deliberately broken test is only useful if it breaks the right thing.**
Emptying `BUTTON_TONES` to check `usedBy` catches drift made the module throw on
import, which failed every test in the file and proved nothing about the
assertion. Pointing one tone at a role that does not exist — the drift that
actually happens — failed exactly the two tests that should. It also showed a
real gap, and the loop now skips a scheme with no row instead of taking the
whole file down with it.

**"No UI" has to include the wiring.** `withSemanticsSlice` takes a
`justRemoved` list that nothing passes yet, so deleting a seed role in the
studio today behaves exactly as it did before the list existed. That is the
point of a model stage, and it is also the one thing stage 4 can forget — so it
is written in the function's own doc comment rather than only in the plan.
