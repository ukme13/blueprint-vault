# 2026-09-06 — A type scale documented, and eight roles stored at one size

Stage 3 of the foundations plan, typography only. One page rendered from the
reference workspace's type system, with written guidance, in light and dark.

## What was done

**The rows live in the package.** `typography/role-rows.ts`, beside
`color/token-rows.ts` and for the same reason: the studio's role editor and
this page describe one system, and each would otherwise decide for itself what
a row is. Which size a role resolves to, what element it renders as, which
variables it exports under — three rules, three chances to drift.

**The variable names come from the export's own function.** `typeTokenId` was
private to `system-export.ts`; it is exported now, and the rows call it. The
unit test checks the rows against the export's actual output rather than
against a second list, and the case that separates them is a role called "Body
Large": a local `toLowerCase` gets the hyphen wrong and a developer copies a
variable that resolves to nothing.

**The preview templates moved into `@blueprint/ui`.** The README's rule is that
a second application needs it, and this page does. Their three layout rules did
not come with them — a package shipping a stylesheet would be deciding what a
gap is for every app that renders one — so the classes travel as a prop, which
is the arrangement Button already has. The studio passes the same module
classes and renders identically: 224 e2e passed, the same as before, including
the two tests that switch templates and languages.

**The page is the colour pages' shape.** Guidance, the scale, the roles, the
specimens, then the article. A developer arriving for a variable name finds the
table without reading the prose; a designer arriving to judge the scale reaches
the specimens having been told what a role is.

## What the page found

**Every role in the reference workspace is stored at 16px.** Eight roles, eight
different step offsets, one stored size. The studio resolves the offset against
the ramp on read and never writes the result back, so the stored number has
been meaningless since the model merge and nothing had ever needed to notice. A
page printing `role.desktop.fontSizePx` would have shown eight roles at one
size and called it a scale.

**The article template asks for roles a default workspace does not have.** It
wants `label`, `title`, `heading`, `body` and `display`; a default system has
`display-1`, `h1`–`h6` and `body`. Four of the five fall through to body, so
the article renders its kicker, its standfirst, its byline and both section
headings at 16px. The fallback is doing exactly what it was built to do, and
what it is hiding is that the templates and the model have been out of step
since the merge. Left alone: the same fallback runs in the studio, and changing
it is a studio change.

**The plan named five default groups and there are three.** Display, heading,
body, label and caption is the group table from the typography rework, not what
`defaultSystem` builds. The guidance covers the three that exist and a test
checks its names against the seed system, so the prose cannot quietly describe
an intention again.

## Lessons

**Astryx's own guidance can be unfollowable, and the failure was the good
kind.** "Set an explicit width on every column" lives in the Table's
data-driven mode, whose `columns` array carries a `renderCell` function — and a
function cannot cross into a client component from a server one. It failed the
build with the offending prop printed, rather than rendering something subtly
wrong. Composed rows are the only option from a server component, and there the
cell sets `overflow-x: hidden` on an auto-layout table: three variable names
were clipped at 1280px and eleven at 900px, silently, with no scrollbar to
suggest anything was missing.

Two wrappers were tried before measuring properly, and neither moved the
number. Walking the element chain and reading `overflowX` at each level took
one run and gave the answer: it is the cell, not the table and not the page.
The names wrap now. A wrapped name is ugly and complete; a clipped one is tidy
and wrong, and it is the tidy one somebody copies.

**Rendering a role as its real element puts it in the page's outline.** The
plan asked for it and the plan was right — an `h2` role has to be an `h2` or
the page is describing something it is not showing. It also gives a reader
navigating by heading eight top-level headings, six of them the same six words.
The tag stays and `aria-level` moves the announced level, which is the
distinction that was wanted all along: a sample of a heading, not a heading of
this document. The cost was not in the plan and was created by the plan's own
instruction.

**A directive is a property of a module, not of a component.** `"use client"`
at the top of the preview templates made the whole file a client boundary, so a
server component could not call a plain function exported beside them. They are
constants and pure JSX; the directive was only ever there because the file
lived in the studio's tree. Moving a component between applications means
asking which of its annotations were about the component and which were about
where it happened to live.

**Nothing on this page has ever rendered a Google font or an uploaded one.**
Both fonts in the reference workspace are the same system family, so the two
paths that matter most to a client are written, unit-tested, and unexercised on
the page itself. That is worth fixing in the fixture before stage 5 hands one
to somebody.

# Later — a client's file said every role was 16px

Four findings from the typography page, closed. One of them was not the finding
it looked like.

## The export was writing the wrong number

The page's own note said the reference workspace stores every role at 16px and
the studio resolves on read. True, and incomplete: the CSS export read that
stored field directly. So the generated file — the artefact a client installs,
the whole point of stage 1 — declared `--font-h1-size`, `--font-h2-size` and
`--font-display-size` all at 16px, beside a correct `--font-size-8: 62px`. The
line heights were wrong with them, because a line height is computed from the
size it sits on.

Nothing on any screen showed it. The studio resolves the step offset before it
renders and so does the documentation page, so the scale was right everywhere a
person looks and wrong in the one place nobody does.

**The field could not be deleted, which is what the brief asked for.** It looks
dead — every value in a seeded system is inert — but it is the store for a
hand-set size. The studio's size input writes there and sets `stepOffset: null`,
and an unlinked role has no step to resolve against. Deleting it would have
deleted the Custom size control and silently reset every role somebody had
tuned by hand. It is documented as what it is instead, and a guard now holds
the row builder and the exported file to the same number for every role.

Fixing it surfaced a second one immediately. `resolveSystemRoles` copied the
desktop size into both viewports, which was harmless in the studio because the
studio only ever renders desktop, and became a regression the moment the export
called it: a system authored at two sizes lost its mobile one. A pre-existing
export test caught it on the first run.

## The slot rules had to be different from the rules

The templates ask for six role names a merged-model workspace does not have, so
five of six slots fell to body. The fix is a resolver in the package, shared by
the studio and the documentation, and an exact id always wins.

The rules underneath were specified as one role per group, and one role per
group does not work. A heading slot taking the heading group's first role gets
`h1`, which on a default system is 62px — identical to `display-1`. The hero,
the standfirst and every section heading would have come out the same size, so
the article would have been fixed into a different kind of broken. A standfirst
is a subordinate title; a section heading sits under it. They take the second
and third heading roles, and the article now runs 62 / 48 / 40 / 16 where it
ran 62 / 16.

Doing that split one function into two. A template asks which role should draw
its heading slot; the specimen list already has a role and asks what it looks
like. One function had been answering both, which is precisely how the slot
chain came to answer for a concrete role.

## Lessons

**A correct screen is not evidence of a correct file.** Two readers of the same
data, both resolving before they render, agreed with each other and disagreed
with the export — and the export is the only one of the three anybody outside
this repository ever sees. The guard that would have caught it is not a better
test of either reader; it is a test that the two readers agree, which is a
different assertion and the one worth having.

**"Remove the dead field" was the right diagnosis of the wrong thing.** The
field was carrying a stale value _and_ holding a feature. Both were true, and
acting on the first without checking the second would have been a silent data
loss shipped as a cleanup. The check took one grep of the size input.

**A measurement can be right and still not be a defect.** Seven spans on the
colour page report as clipped — 1px wide, holding 50px of text — and should
stay exactly as they are. `sr-only` is indistinguishable from a cut-off name by
the only measurement that finds cut-off names. The tool cannot tell you which
one you are looking at; only reading the element does.

# Later again — three pages that mostly did not need a row builder

Stage 3 finished: spacing, radius and elevation, one page each, the same shape
as the typography page beside them.

## What was done

**A row builder small enough to look unnecessary.** Its colour and typography
siblings exist because two readers of one system would otherwise each decide
what a row is. Here they would not — `resolveSpacing`, `resolveRadius` and
`resolveElevation` are already what the export calls to write the file, so a
page calling the same functions cannot print a variable the file lacks.
`scale-rows.ts` carries two things and no more: elevation paired across its two
modes, and the shade a shadow was drawn from, which the resolution otherwise
consumes on the way to an `rgba`.

**Three pages, three specimens.** Spacing draws each step as a bar, because a
column of numbers says 24 is twice 12 and a column of bars says what twice
looks like. Radius draws each corner on a bordered surface, since a corner is
only visible where two edges meet. Elevation draws every level four times: on a
light ground and a dark one, in whichever mode the reader is in.

## What the pages found

**Elevation's grounds cannot be semantic utilities, and that is not a
shortcoming of the page.** The whole claim it makes is that a shadow's colour
does not change between modes and its strength does — which needs a light
ground and a dark one visible at once. A semantic utility resolves to whichever
mode the reader is in, so `bg-surface-base` would draw the same ground twice
and prove nothing. The playground's editor solves this with
`--color-neutral-50` and `--color-neutral-900`, which is a primitive and
forbidden here. So the grounds are `surface.base` and `surface.raised` resolved
per mode and passed in as values, the way `Swatch` already takes a hex: a role
named, resolved from the workspace, never typed.

**The scale roadmap got nothing wrong.** That is worth recording precisely
because the last two branches found the opposite. It opens by correcting its
own earlier draft — "it was going to be spacing is the same maths as type,
reuse `generateTypeSteps`; reading the tokens first showed that is wrong" — and
that correction is the substance of the spacing page's first section. A ratio
of 1.25 over a 4px base gives 6.25px steps that look principled and cannot be
used. The plan had already been through the mistake the page would otherwise
have documented.

**A token that knows what it is for beats a paragraph that knows it.** Every
radius token carries its own description, written when the token was defined,
so that page's table has a "what it is for" column filled from the workspace.
Spacing steps and type roles have no equivalent, which is exactly why their
pages carry more prose. The difference is visible in the page length.

## Lessons

**A convention is only worth having if it is enforced against its own
awkward cases.** The guidance names a counter-example — there is no radius-2 —
and the test that every backticked token exists would have failed on it, along
with rgba, var() and box-shadow. The temptation is an ignore list. The better
answer was to decide what a backtick means: it means "this exists". A
counter-example and a piece of CSS syntax are neither, so they lose their
backticks, and the test goes back to stating something obvious rather than
guessing at intent.

**Picking the value a test asserts on is part of writing the test.** The
spacing test changes the base unit from 4 to 6 and checks the page moved. The
first version asserted on 24px, which passed before the edit as well as after —
step 6 at a base of 4 is also 24. A test that cannot fail is worse than no test
because it reads as coverage. 9px is step 1.5 at a base of 6 and cannot be
produced by the seeded scale at all, which is the property the assertion
actually needed.
