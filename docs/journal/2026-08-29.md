# 2026-08-29 — Splitting the typography studio, merging its storage, and the tests that lied

## What was done

**TypographyStudio, 1294 lines to 603.** Five extractions, one per concern:
`typography-project.ts` for the localStorage shape and its two migrations,
`use-google-fonts.ts` for the stylesheet, `RoleGroupEditor` and
`TypographyPreview` for the two large JSX blocks, and `useTypographySystem` for
the edits.

The edits were the interesting one. Twelve mutators each re-derived "is there a
project?" before doing their work, so the same `current ? … : current` guard
appeared fifteen times in one component. Every one of them is a
`TypeSystem -> TypeSystem` edit that never touches the preferences beside the
system, which is what makes the guard collapsible — `editSystem` answers the
question once and the rest become pure functions. Nineteen occurrences down to
two.

Those functions then moved again, into `packages/ui` beside `addFont`,
`reindexGroup` and `moveGroup`, which several of them already call. 21 unit
tests followed. The hook kept what it is for and went 226 lines to 95.

**Three fixes that came out of the refactor rather than being planned.** A
Windows-only path separator in the css-token report; a StrictMode race that lost
the chosen colour format on every reload; and an e2e test that had never once
passed.

**Dead CSS and the last Tailwind holdout.** Four rules with no reader
(`.roleSetting` and its 640px override, `.roleSettingTop`, `.unitChips`,
`.presetCallout`), and `FontStackEditor` moved off arbitrary-value Tailwind onto
the CSS module beside it.

**`CLAUDE.md` gained architecture, testing and git sections.** The architecture
rule about domain logic living in `packages/ui` is the one this day was spent
learning.

## What was learned

**CI cannot see a StrictMode bug, because it builds for production.**
`playwright.config.ts` reads
`process.env.CI ? "pnpm build && pnpm start" : "pnpm dev"`. Effects double-invoke
in dev and not in a production build, so a whole class of bug is green on CI and
red on every developer machine. `ColourFormatProvider` had one: a mount effect
read the stored format, a second effect wrote state back, and on mount the write
ran while the state was still the `"hex"` default. Production self-corrects on
the next render. StrictMode does not — the clobbering write lands between the
read's two runs, and the second read sees `"hex"`.

Two other providers already had the guard for exactly this. Only this one
lacked it, which is the tell: an inconsistency with the codebase's own pattern
is worth more attention than it usually gets.

The decision was to keep CI as it is and treat a red local suite as real. That
only works if the suite is green, which it now is for the first time — 208 unit
and 79 e2e.

**A test that has never failed has not been shown to test anything.** An
assertion written for `addRole` claimed it clears `sameAsRoleId` on every role.
It clears it only on the copy; the template keeps the link someone set
deliberately. The test passed against behaviour it would have been wrong to
allow, and only broke when the expectation was corrected. The other twenty were
then checked by breaking three rules on purpose — five cases failed, none passed
silently.

**`as never` does not silence one error, it silences all of them.** `never` is
assignable to every type, so `role.id as never` would have kept compiling if the
field became a number. It was there because `RoleAssignment.role` is a
`SemanticRole` — one of six fixed names — while systems have named their roles
freely since groups arrived. The fix was in the type: `assessRoleWeights` only
ever reads `role` and `fontWeight` and hands the name back as a string, so it now
takes a parameter that says exactly that.

**Playwright's `count()` does not retry.** Every locator assertion polls, so
`toHaveCount` waits for the page — but `await locator.count()` returns whatever
is there right now. A test that measured a baseline before acting read `0` from
the loading placeholder, and asserted `toBe(-1)` against a correct `5`. It had
failed on every run since it was written. The sibling test passed only because
it happened to assert some elements visible first, so that `await` was doing
load-bearing work nobody had asked it to do. Fixed in the fixture, so no future
test can measure the page before it has hydrated.

**`join()` gives you the platform separator, and it leaks into output meant for
people.** The css-token checker reported `app\page.css` on Windows against a test
expecting `app/page.css`. Green on `ubuntu-latest`, red on every Windows
checkout, since the day it landed. Paths for a reader get normalised; the walker
keeps native paths for actual I/O.

**A function that generates a user-facing label is not automatically app-level.**
The argument for keeping the system edits in the app was that `addGroup` mints a
`Group N` label. But `addFont` mints `Font N` and had lived in `packages/ui` all
along. The line that would have justified a second test harness did not exist,
and looking for it before building one saved the harness entirely.

**Justifying an extraction on testability incurs a debt.** The edits were put at
module scope specifically so they could be tested without a component around
them. They then were not, and the playground has no unit test harness to do it
with — so the claim was true in principle and false in practice for two commits.

## Later the same day — one workspace, and the preview it was for

### What was done

**The two studios became one document.** They were separate routes holding
separate projects under separate localStorage keys, sharing nothing, which made
"preview the type on the palette you made" unbuildable. Now
`blueprint.workspace.v1` holds both halves, migrated from whatever a browser
already had — either key alone, both, or either historical typography shape. The
old keys are read and left in place, so the migration is reversible by deleting
one key rather than by restoring a backup.

The plan is in
[workspace-project-merge.md](../roadmap/workspace-project-merge.md), staged so
the schema and migration landed first, pure and unit tested, with nothing
consuming them.

**The preview reads the palette.** Text and background come from the palette's
own tracks and shades, and every role reports the contrast for that pair at its
own size and weight. Stage 4 of the preview plan, and the reason for all of the
above.

**The two add buttons** in the typography inspector were different sizes and
stretched the full width of a 900px panel. Now one size, one width, and full
width below a 360px panel.

### What was learned

**Merging two storage keys removes a protection nobody had noticed was there.**
While each studio wrote only its own key, two open tabs could not destroy each
other's work. One key ends that, and nothing in the app listens for the
`storage` event. The mitigation is to re-read the stored document before every
write and patch only your own half, rather than persisting the copy you loaded
at page load.

**That mitigation does not cover a field the two halves share.** The two-tab
test found the slices already safe and the workspace name not: a studio adopts
the name at load, so its copy goes stale the moment the other tab renames, and
re-reading cannot help because the studio is deliberately passing its own name.
The rule had to go one level down — send the name only when you are the tab that
changed it. Worth noting the hazard was introduced by the commit immediately
before it; had the cross-tab work come first it would have passed, and the
regression would have shipped straight after.

**A validator that throws and a validator that salvages are not the same
function.** `parseBlueprintPaletteProject` rejects a bad file, correctly: a file
someone picked is either what they meant or a mistake worth reporting. Storage
is not a choice anyone is making now, so its reader keeps one good track out of
four broken ones. Sharing one implementation would have meant either a lenient
file import or lost data.

**Nullish coalescing is not a fallback for empty.** Workspace name resolution
used it, so a blank name survived as `""` and would have left the topbar showing
nothing. Found by the test written for that case. The file parser had required a
non-blank name all along, so the two disagreed.

**A grid child with no width takes the column, and an implicit `auto` column
takes its widest child.** Two buttons that should have matched came out 313px and
304px inside the same 304px content box. The cause was not the buttons: one group
held a control that would not shrink, so its column overflowed the panel and
everything measured against it followed. An explicit minimum-zero column took the
inspector's horizontal overflow to zero, which it had never been.

**Screenshot the feature before writing tests for it.** The palette preview
applied the chosen background to the stage, and every role card painted its own
surface on top of it — so the text was still being previewed on studio chrome.
Every assertion I would have written first was about the contrast numbers, and
all of them would have passed while the feature answered the wrong question. The
test that guards it now reads the computed background rather than the markup.

**The same fixture bug twice.** The palette `seededPage` raced hydration exactly
as the typography one had earlier the same day: `goto` resolves before the
effects that read and persist have run, so a storage assertion read `null`. The
lesson had been written down that morning and still only applied to the file it
was found in.

## Third pass — the merge that broke, and the scripts we do not check

### What was done

**Line height is judged by the script the specimen is written in.** The studio
ships Thai preview content and tells people to review Thai, then checked the
result against one threshold written for Latin — so it did not implement a rule
its own guidance states. Thai now needs 1.4 rather than 1.2 and fails below 1.25
rather than 1.1, because its vowels and tone marks stack above and below the
line. Mixed text takes the stricter of the two. That closes
[typography-preview-and-units.md](../roadmap/typography-preview-and-units.md),
which is now done end to end.

**The stylesheet has tests.** Five computed-style cases over the add buttons,
the inspector's horizontal overflow, the preview background reaching the text
rather than only the stage, and the verdict colours.

**Uploaded fonts have a plan** at
[uploaded-fonts.md](../roadmap/uploaded-fonts.md), written around where the file
is allowed to go rather than around storage.

### What was learned

**Green CI on two branches says nothing about their merge.** Both PRs passed
lint, types, tests and build. Both were verified locally. Then merging one into
the other broke the build, because both had appended to the end of the same
stylesheet and the resolution swallowed a closing brace — trapping every rule
after it inside a selector that matched nothing.

The tell was there to read in advance and nobody read it: two branches touching
the tail of one file is the shape that merges badly, and I had written both.
Rebasing one onto the other before merge would have surfaced it while it was
still cheap.

**The build catches syntax, not meaning.** That break was caught only because a
missing brace happens to be a parse error. The same merge could as easily have
produced valid CSS with rules nested one level too deep — parses, builds, ships,
and the buttons silently revert. So the new style tests were checked against
that version rather than the easy one: nesting the rules instead of removing the
brace, then confirming a test fails. It does.

**A tool's legal exposure follows the bytes, not the feature.** The question for
uploaded fonts is not whether to allow uploads. Font licences restrict copying
and distributing, not using, so what matters is where the file ends up. Local to
a browser is close to what a desktop licence already permits; an exported
stylesheet is distribution. The trap in a studio like this one is that it is an
export tool, so the risk is not the upload at all — it is the export path that
would carry the file onward.

**A field written everywhere and read nowhere is a decision nobody has made
yet.** `TypeFontSource` has carried `"google" | "local" | "system"` since the
model was written, is set on every font entry, and nothing branches on it.
Worth finding out before adding a fourth value, because the first thing to
actually read it defines what the others meant all along.
