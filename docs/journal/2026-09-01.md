# 2026-09-01 — A redundant field that turned out to be the real one, and a format nobody had called in weeks

## What was done

**The palette slice lost its `name`.** Every roadmap was ticked, so this was the
first of the cleanups the workspace merge plan had been deferring:
`PaletteProjectData` carried a name that the plan itself described as kept "for
now, since `parseBlueprintPaletteProject` and the export file both use it".

The slice has no name now. `PaletteStudio` holds one of its own, the way
`SpacingStudio` already did, and `withSharedName` pushes the workspace name
into the typography slice only — which keeps a copy because its export and the
accessibility report's `systemName` read one.

**Pre-workspace data still carries the field, so something still reads it.**
`readLegacyPaletteName` does, on the way in and nowhere else: the localStorage
migration and an imported `blueprint-palette` file both take the name of the
workspace they become from it.

**The `blueprint-palette` format went with it.**
`formatBlueprintPaletteProject`, `parseBlueprintPaletteProject` and
`BlueprintPaletteProjectFile` had no app callers at all. The workspace file
replaced the format at stage 6, and the legacy import path had already moved
onto the lenient `readPaletteProjectData` rather than the strict parser. Old
files still import; nothing about that path went through the code that was
deleted.

**Left alone:** `LEGACY_PALETTE_STORAGE_KEY`, `retireLegacyKeys`,
`workspaceFromLegacy`, `migrateLegacyProject`. They read like the dead
"old storage key" code the cleanup was hunting, and they are the live migration
for anyone who has not opened the app since the workspace shipped.

## What was learned

**A field that looks redundant may be the real one, in the wrong place.** The
plan called `palette.name` a duplicate of the workspace name, to be deleted
once nothing needed it. It was not a duplicate. `PaletteStudio` was storing the
workspace name _inside the palette slice_ — `name: project.name` when it
rebuilt the workspace for export, and a rename implemented as a palette edit.
So the field had one real consumer after all, and the job was moving it out
rather than removing it. Two consequences fell out immediately: renaming stopped
being a palette mutation, and a studio with no palette gained somewhere to keep
a name, which it had never had.

**Retiring a format is not retiring its readers.** Deleting the writer was
free. The name inside those files was not: it is the only thing a
`blueprint-palette` file still gives the workspace that the workspace cannot
get elsewhere. Separating the file shape from the in-memory shape — the slice
has no name, the reader still finds one — was the whole design, and trying to
delete the field everywhere at once would have silently renamed every imported
legacy file to the default.

**A validity gate can be built out of the wrong field.**
`readPaletteProjectData` returned null when a stored blob had no readable
`name`, which meant a browser holding tracks and no name had its colours thrown
away to enforce a field that is now gone. Tracks are what make something a
palette; a name never was. Loosening the gate is a behaviour change that needed
its own test rather than arriving as a side effect of a type edit.

**The type checker proves the field is gone. It cannot prove the value came
back.** `tsc` found all eight reads of `project.name` and every one was
mechanical. The ninth site was not a read at all: the header import path set
the palette but never called `setName`, because the name used to ride in on the
slice. That compiles perfectly. Importing over an existing project left the old
name in the topbar, and only the e2e saw it. A refactor that moves a value has
two halves, and the compiler only checks one of them.

**A compatibility test that generates its own fixture is not one.**
`workspace-file.test.ts` proved that `blueprint-palette` files still import by
building one with `formatBlueprintPaletteProject` — the current writer. That is
the only reason the writer still existed. It would have followed every future
change to the format and gone on passing while proving nothing about the files
people actually have. The fixture is hardcoded JSON now. This is the same
lesson as the font-removal case on 08-30 from the other direction: there, a
test could not see the violation; here, a test could not see the past.

**Deleting a symbol leaves its stories behind.** The export guard's comment
explained why it matches every `format*` rather than only names ending in
`Export`, and its cautionary example was `formatBlueprintPaletteProject` —
which this commit deleted. Nothing failed; a comment does not compile. Grepping
for the removed names across `.md` as well as `.ts` found it, along with two
roadmap lines that were correct as history and one that was not.

**Both halves of the guard, broken on purpose.** Restoring the name in
`withSharedName`, dropping the trim in `readLegacyPaletteName`, re-adding the
name gate, and making a legacy file stop naming its workspace each fail exactly
the test written for them. The third break failed ten tests rather than one,
which is the honest signal that the gate is load-bearing well beyond the case
it was written for.

## A flake, not a regression

`preview-page.spec.ts` — "turns simulation on and back off again" — failed once
in a full run and then passed three times alone and clean through a second full
run. It polls a computed `backgroundColor`, so it is load-sensitive in the same
way the elevation shadow was yesterday: a colour assertion that reads as a
logic failure and is really a scheduling one.

Worth saying plainly that one failing run is not enough to call something
flaky, and one passing run is not enough either. What settled it was that the
failing assertion has no path to the code that changed — this commit does not
touch the preview page, the vision control or the semantic layer. Left for its
own branch rather than fixed here, since a fix and a refactor in one change set
makes both harder to read.

**The guess above was wrong**, and is kept rather than edited because being
wrong in a particular way is the useful part. See below.

## Later — the flake, diagnosed

### What was done

**The preview specs wait for their semantic layer.** `openPreview` in
`preview-fixtures.ts`, applied to all four seeded tests in the file rather than
to the one that failed. One fixture per area, as the palette, typography and
scale suites already do.

**The e2e job caches the Playwright browser download,** keyed on the resolved
Playwright version rather than a lockfile hash.

### What was learned

**"Load-sensitive" is a shrug, not a diagnosis.** The guess above named the
right family — a colour assertion that is really a scheduling one — and stopped
there, which is worth nothing: it does not say what to wait for. A probe
sampling the baseline across parallel runs answered it in one go. In 2 of 8
runs the primary action measured `rgba(0, 0, 0, 0)`, because every colour on
that page comes from a semantic token and `goto` resolves before the effect
that reads storage has populated any. The same lesson as the four-tab bar on
08-31: measure before patching, and a guess that sounds like an explanation is
the thing most likely to stop the measuring.

**A test can fail at the assertion that is working.** The baseline was wrong,
so the first half — the simulation changes the colour — passed, and the second
half — turning it off brings the colour back — failed, because transparent is
not what it comes back to. Everything the error message pointed at was correct.
Playwright's `evaluate` waits for the element to be attached, and it was: real
element, real answer, taken one render too early. An assertion that fails is
not evidence about the line it is on.

**Wait on something the thing you care about is made of.** The footer count and
the CSS variables are computed from the same `tokens` array in the same render,
so a footer reporting a layer is a DOM that already carries it. That is a
different claim from "the footer usually updates around the same time", and
only the first is a guarantee. The count is matched as "not zero" rather than
as 12, because how many roles a seed produces is the first test's business; a
fixture repeating the number breaks every spec in the file the day the seed
changes.

**Fix the ones at risk, not the ones that failed.** "Answers to the mode
toggle" takes its baseline the same way and waited only on the heading, which
renders before the read from an empty token list. It had never failed and was
one scheduling change away. This is 08-31's lesson applied without having to
relearn it.

**A guard removed on purpose can come back as a different failure.** Taking the
wait out brings a failure in the file straight back, but the symptom moves —
once the transparent baseline, once a chip click landing before hydration.
Both are "acted before the read landed". Reporting a single clean repro would
have been the neater claim and the wrong one; what the removal proves is that
the wait is load-bearing, not that it protects one line.

**Caching a browser does not cache what runs it.** `--with-deps` installs OS
packages through apt, which land outside `~/.cache/ms-playwright`. A cache hit
restores Chromium and none of its libraries, so the hit path still has to run
`install-deps` — otherwise the saving buys a present binary that will not
launch. The cache key is the Playwright version, not a lockfile hash, because
the version is what pins the browser build; hashing the lockfile would discard
the browsers every time an unrelated dependency moved.

**None of this can be caught by CI as it stands,** which is now the third entry
to say so. CI builds for production and the races live in `next dev` under
StrictMode. The asymmetry is unchanged and is starting to look like the actual
finding rather than a footnote.

## Later — the CI file

### What was done

**The e2e job runs only when something it covers moved,** and all four actions
crossed to the Node 24 runtime together.

### What was learned

**The feature asked for did not exist, and the workaround is not the same
shape.** There is no per-job `paths` filter: `paths` is valid only under
`on.<event>`, where it gates the whole workflow rather than one job. So "add a
path filter to the e2e job" becomes a detection job publishing an output and a
second job gating on it — three jobs where there were two, and a cross-job
expression that fails silently as a permanently-skipped job if it is misspelt.
Worth checking the syntax reference before agreeing to the shape of a request,
not after.

**A filter has to include the file that defines it.** Filtering e2e on
`apps/playground/**` and `packages/ui/**` alone means a change to the e2e job
skips the job it changed — this commit would not have run e2e, and the change
could not have been verified on its own pull request. The lockfile is in for
the same reason from the other direction: a dependency bump can break the
browser suite while touching neither app nor package. A path filter is a claim
about what cannot break the job, and that claim is wrong by default.

**Skipped is not success.** A gated job reports "skipped", which satisfies
nothing. There is no branch protection here, so it cannot block a merge today —
but that is a fact about the repository's current settings rather than about
the workflow, and it stops being true the moment somebody turns required checks
on. Checked rather than assumed; the answer happened to be favourable.

**Read the release notes for the majors you skip, not just the one you land
on.** `setup-node` v5 added automatic caching driven by the `packageManager`
field and v6 narrowed it to npm only — a breaking change in the middle of the
range, invisible from either end. It turned out harmless here because this
repo declares pnpm and passes `cache: pnpm` explicitly, which v7 still
supports. Confirming that meant reading the action's own `action.yml` rather
than a summary of it.

**A version bump can be the right version rather than the newest one.**
`pnpm/action-setup` v6 is the release that added pnpm v11 support, and
`packageManager` pins `pnpm@11.24.0`. That is a better reason to move than the
deprecation warning that prompted it, and it was only visible by reading what
each major actually changed.

**Lint the thing in its own language.** `pnpm lint` says nothing about a
workflow file. actionlint type-checks the expressions, shellchecks the `run`
blocks and knows the schema; a YAML parse on top asserted that every `needs`
target exists and that the `if` resolves to an output some needed job really
declares. Valid YAML and a valid workflow are different claims, and only the
second one matters here.

## Later — line height, in the three ways someone means it

### What was done

**A role's line height is a config, not a number.** `auto | px | ratio`, with
`computeLineHeight` returning both the pixel height and the unitless ratio.
The export still emits the ratio; only the editor and the grid want pixels.

`auto` multiplies the group's default and snaps **up** to a 4px grid. The
research said to: Material stores round rem, Tailwind ships
`calc(1.75 / 1.125)`, Carbon ships `1.42857`, which is 20/14. All three pick a
round pixel target and let the ratio fall out. None picks a pretty ratio.

**The field shows the number, not the word.** `auto` is an empty field with
the resolved height as its placeholder — muted, so a followed default looks
different from a pinned one.

### What was learned

**Research the question before designing the answer.** "Do people keep the
decimal or round it?" had a real answer in three shipped systems, and reading
their token source rather than their documentation gave it: the decimals are
byproducts of a round pixel target. Tailwind leaves the division in the
stylesheet, which is as close to a stated intention as a codebase gets. The
design that followed was theirs, not ours, and better for it.

**A literal reading of a spec can be the wrong one.** The instruction said
unitless numbers are ratios. Followed exactly, typing `24` gives a line height
of 24× — a 384px gap on body text. The ranges do not overlap in any real
scale, so reading a bare number by its size means nobody has to find a unit
control first. Worth saying which part of an instruction you are not
following, and why, rather than either obeying it into a bug or quietly
changing it.

**The type checker proves the field is gone. It cannot prove the value came
back.** Changing `lineHeight` from a number to an object gave eight mechanical
compile errors and one silent bug: the header import path set the palette but
never called `setName`, because the name used to arrive inside the slice. That
compiles perfectly. Only the e2e saw it. A refactor that moves a value has two
halves and the compiler checks one.

**A type change can hide behind a template literal.** `${value.lineHeight}`
went on emitting CSS, as `[object Object]`. And `role.desktop.lineHeight !==
role.mobile.lineHeight` went on comparing — by identity, so two roles both on
`auto` differed, and every export would have gained the media query that
function exists to withhold. Neither is a type error. Interpolation and
equality accept objects quietly.

**Fixing a UI trap can open its mirror image.** Committing on blur pinned
`auto` the moment somebody clicked away, because what `auto` displayed was a
real number. Committing only an edit then made that number impossible to pin,
because typing what is already there is not a change. The placeholder settled
both at once: an empty field makes the number an ordinary edit, and the
special case that had been bolted on came out again. A fix that deletes a
branch is usually the right one.

**Clearing is an answer; typing is a step towards one.** The clear button
blurs the input on its way, so the typed value committed first and the clear
queued behind it — and the placeholder, computed from the model, offered the
height that typed number resolved to. The field looked emptied and was not.
Emptying commits where it happens; a half-typed number waits.

**Two grids with the same template are not one grid.** The role table's header
and rows carried identical `grid-template-columns` and drifted apart, the gap
widening across the row. `minmax(5rem, 0.8fr)` resolves against the content of
its own grid: the header settled at the container width while a row of inputs
was pushed past it by its minimums. `display: contents` on both leaves one set
of tracks and nothing to disagree about.

**Read the component before overriding it.** `cn` in `button.tsx` is a plain
join, not tailwind-merge, so a `className` size sits beside the CVA one and
only stylesheet order decides. The file's own header says no `!important` is
needed — true of Astryx's stylesheet, and not of its own variants. Measured in
the browser rather than reasoned about: 32x32 with the suffix, 36 without.

**Astryx's NumberInput keeps its own text buffer.** `fill("")` empties it on
screen without firing `onChange`, so the model never learns and a value
assertion can pass against text nothing committed. `hasClear` also adds a
button named "Clear <label>", which `getByLabel` matches too. I nearly deleted
`hasClear` as broken over the first of these; it works, and I had not blurred.
Check what a control does before removing it.

## Later still — a font file per slot

### What was done

**An upload sets one slot rather than the whole stack.** `setLocalFont` wrote
`[family, "sans-serif"]` over the entry's families, so uploading a Latin face
onto Inter + Noto Sans Thai deleted the Thai. Silently, and only for Thai.

**Then both slots became uploadable.** `source` was one value per entry and
could not describe an uploaded Latin face in front of a Google Thai one; the
IndexedDB key was the entry id and held one file. Now `sources: { primary?,
fallback? }` and `base::primary`, with a read-through to the old key so files
uploaded before this still render.

### What was learned

**A control's position is a claim about its scope.** One upload input sat
below two pickers, where it read as belonging to the entry. It fed the first
slot and destroyed the second. Moving the control inside the slot it writes
makes the claim true by construction — which is a better fix than a warning,
because there is nothing left to warn about.

**Say which half of a request is a bug fix.** Uploading into both slots was
asked for as a feature. Underneath it was a data-loss bug that had been
shipping. Splitting them meant the fix landed on its own, small and
revertible, before a schema change went anywhere near it.

**A field that describes a record cannot describe its parts.** `source` was
fine while an entry held one family and one file. The moment a stack could mix
an uploaded face with a Google one, a single value had no answer. This is the
same shape as the line height earlier today: a scalar that has to become
structured, and a detect-by-shape migration to carry the old one across. The
migration knew more than the data did — the old `source` meant the primary,
because nothing else could ever have set it.

**Two colons, because one was taken.** The store key packs an id and a slot;
another part of the same feature already packs an id and a family with a
single colon. A separator that appears inside one of the halves stops being a
separator.

**Deleting the key you replaced is part of writing.** A file under the old
bare-id key is referenced by nothing once the slot key holds one, and an
orphaned copy of somebody's licensed font is the thing this plan exists to
prevent. Both the write path and every removal path clear it.

**An accessibility fix can remove information.** Two upload inputs in one
entry needed distinct names, so the input gained a fixed `aria-label` — which
replaced the state it used to announce. "Add the missing file" stopped
existing as a name and four e2e specs lost the control they were looking for.
They were right to fail. The name carries both now. A screen reader needs to
hear which slot _and_ what state; picking one was the error.

**An assertion in an edit script is a seatbelt.** A pattern with a typo in it
aborted a two-file script after the first write, leaving mismatched props
across a component boundary — caught immediately, because the script asserts
its match count rather than trusting `replace`. The same guard caught a regex
that would have rewritten expected CSS strings alongside the fixtures it was
aimed at.
