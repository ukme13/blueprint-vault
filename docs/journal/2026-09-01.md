# 2026-09-01 — A redundant field that turned out to be the real one, and a format nobody had called in weeks

## What was done

**The palette slice lost its `name`.** Every roadmap was ticked, so this was the
first of the cleanups the workspace merge plan had been deferring:
`PaletteProjectData` carried a name that the plan itself described as kept "for
now, since `parseBlueprintPaletteProject` and the export file both use it".

The slice has no name now. `PaletteStudio` holds one of its own, the way
`SpacingStudio` already did, and `withSharedName` pushes the workspace name
into the typography slice only — which keeps a copy because its export and the
accessibility report's `systemName` read one.

**Pre-workspace data still carries the field, so something still reads it.**
`readLegacyPaletteName` does, on the way in and nowhere else: the localStorage
migration and an imported `blueprint-palette` file both take the name of the
workspace they become from it.

**The `blueprint-palette` format went with it.**
`formatBlueprintPaletteProject`, `parseBlueprintPaletteProject` and
`BlueprintPaletteProjectFile` had no app callers at all. The workspace file
replaced the format at stage 6, and the legacy import path had already moved
onto the lenient `readPaletteProjectData` rather than the strict parser. Old
files still import; nothing about that path went through the code that was
deleted.

**Left alone:** `LEGACY_PALETTE_STORAGE_KEY`, `retireLegacyKeys`,
`workspaceFromLegacy`, `migrateLegacyProject`. They read like the dead
"old storage key" code the cleanup was hunting, and they are the live migration
for anyone who has not opened the app since the workspace shipped.

## What was learned

**A field that looks redundant may be the real one, in the wrong place.** The
plan called `palette.name` a duplicate of the workspace name, to be deleted
once nothing needed it. It was not a duplicate. `PaletteStudio` was storing the
workspace name *inside the palette slice* — `name: project.name` when it
rebuilt the workspace for export, and a rename implemented as a palette edit.
So the field had one real consumer after all, and the job was moving it out
rather than removing it. Two consequences fell out immediately: renaming stopped
being a palette mutation, and a studio with no palette gained somewhere to keep
a name, which it had never had.

**Retiring a format is not retiring its readers.** Deleting the writer was
free. The name inside those files was not: it is the only thing a
`blueprint-palette` file still gives the workspace that the workspace cannot
get elsewhere. Separating the file shape from the in-memory shape — the slice
has no name, the reader still finds one — was the whole design, and trying to
delete the field everywhere at once would have silently renamed every imported
legacy file to the default.

**A validity gate can be built out of the wrong field.**
`readPaletteProjectData` returned null when a stored blob had no readable
`name`, which meant a browser holding tracks and no name had its colours thrown
away to enforce a field that is now gone. Tracks are what make something a
palette; a name never was. Loosening the gate is a behaviour change that needed
its own test rather than arriving as a side effect of a type edit.

**The type checker proves the field is gone. It cannot prove the value came
back.** `tsc` found all eight reads of `project.name` and every one was
mechanical. The ninth site was not a read at all: the header import path set
the palette but never called `setName`, because the name used to ride in on the
slice. That compiles perfectly. Importing over an existing project left the old
name in the topbar, and only the e2e saw it. A refactor that moves a value has
two halves, and the compiler only checks one of them.

**A compatibility test that generates its own fixture is not one.**
`workspace-file.test.ts` proved that `blueprint-palette` files still import by
building one with `formatBlueprintPaletteProject` — the current writer. That is
the only reason the writer still existed. It would have followed every future
change to the format and gone on passing while proving nothing about the files
people actually have. The fixture is hardcoded JSON now. This is the same
lesson as the font-removal case on 08-30 from the other direction: there, a
test could not see the violation; here, a test could not see the past.

**Deleting a symbol leaves its stories behind.** The export guard's comment
explained why it matches every `format*` rather than only names ending in
`Export`, and its cautionary example was `formatBlueprintPaletteProject` —
which this commit deleted. Nothing failed; a comment does not compile. Grepping
for the removed names across `.md` as well as `.ts` found it, along with two
roadmap lines that were correct as history and one that was not.

**Both halves of the guard, broken on purpose.** Restoring the name in
`withSharedName`, dropping the trim in `readLegacyPaletteName`, re-adding the
name gate, and making a legacy file stop naming its workspace each fail exactly
the test written for them. The third break failed ten tests rather than one,
which is the honest signal that the gate is load-bearing well beyond the case
it was written for.

## A flake, not a regression

`preview-page.spec.ts` — "turns simulation on and back off again" — failed once
in a full run and then passed three times alone and clean through a second full
run. It polls a computed `backgroundColor`, so it is load-sensitive in the same
way the elevation shadow was yesterday: a colour assertion that reads as a
logic failure and is really a scheduling one.

Worth saying plainly that one failing run is not enough to call something
flaky, and one passing run is not enough either. What settled it was that the
failing assertion has no path to the code that changed — this commit does not
touch the preview page, the vision control or the semantic layer. Left for its
own branch rather than fixed here, since a fix and a refactor in one change set
makes both harder to read.

**The guess above was wrong**, and is kept rather than edited because being
wrong in a particular way is the useful part. See below.

## Later — the flake, diagnosed

### What was done

**The preview specs wait for their semantic layer.** `openPreview` in
`preview-fixtures.ts`, applied to all four seeded tests in the file rather than
to the one that failed. One fixture per area, as the palette, typography and
scale suites already do.

**The e2e job caches the Playwright browser download,** keyed on the resolved
Playwright version rather than a lockfile hash.

### What was learned

**"Load-sensitive" is a shrug, not a diagnosis.** The guess above named the
right family — a colour assertion that is really a scheduling one — and stopped
there, which is worth nothing: it does not say what to wait for. A probe
sampling the baseline across parallel runs answered it in one go. In 2 of 8
runs the primary action measured `rgba(0, 0, 0, 0)`, because every colour on
that page comes from a semantic token and `goto` resolves before the effect
that reads storage has populated any. The same lesson as the four-tab bar on
08-31: measure before patching, and a guess that sounds like an explanation is
the thing most likely to stop the measuring.

**A test can fail at the assertion that is working.** The baseline was wrong,
so the first half — the simulation changes the colour — passed, and the second
half — turning it off brings the colour back — failed, because transparent is
not what it comes back to. Everything the error message pointed at was correct.
Playwright's `evaluate` waits for the element to be attached, and it was: real
element, real answer, taken one render too early. An assertion that fails is
not evidence about the line it is on.

**Wait on something the thing you care about is made of.** The footer count and
the CSS variables are computed from the same `tokens` array in the same render,
so a footer reporting a layer is a DOM that already carries it. That is a
different claim from "the footer usually updates around the same time", and
only the first is a guarantee. The count is matched as "not zero" rather than
as 12, because how many roles a seed produces is the first test's business; a
fixture repeating the number breaks every spec in the file the day the seed
changes.

**Fix the ones at risk, not the ones that failed.** "Answers to the mode
toggle" takes its baseline the same way and waited only on the heading, which
renders before the read from an empty token list. It had never failed and was
one scheduling change away. This is 08-31's lesson applied without having to
relearn it.

**A guard removed on purpose can come back as a different failure.** Taking the
wait out brings a failure in the file straight back, but the symptom moves —
once the transparent baseline, once a chip click landing before hydration.
Both are "acted before the read landed". Reporting a single clean repro would
have been the neater claim and the wrong one; what the removal proves is that
the wait is load-bearing, not that it protects one line.

**Caching a browser does not cache what runs it.** `--with-deps` installs OS
packages through apt, which land outside `~/.cache/ms-playwright`. A cache hit
restores Chromium and none of its libraries, so the hit path still has to run
`install-deps` — otherwise the saving buys a present binary that will not
launch. The cache key is the Playwright version, not a lockfile hash, because
the version is what pins the browser build; hashing the lockfile would discard
the browsers every time an unrelated dependency moved.

**None of this can be caught by CI as it stands,** which is now the third entry
to say so. CI builds for production and the races live in `next dev` under
StrictMode. The asymmetry is unchanged and is starting to look like the actual
finding rather than a footnote.
