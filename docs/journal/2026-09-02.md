# 2026-09-02 — A menu placed twice, a patch release that broke a field, and a formatter that had never seen half the repo

## What was done

**`pnpm format` had never formatted the repository.** The glob was
`**/*.{ts,tsx,md}`, so CSS modules, configs, package manifests and the
workspace yaml were outside the command that claims to format everything. It
now runs over the whole tree with `--ignore-unknown`, which picks up whatever
file type gets added next without another glob edit. Thirteen files were
genuinely out of shape, `system.ts` and `RoleGroupEditor.tsx` among them.

**The hundred-file diff was line endings, and it would have made the hook
unusable.** Git stores LF and, with `core.autocrlf` on, hands Windows checkouts
CRLF back. Prettier's `endOfLine` default is `lf`, so it rewrote every file it
opened. Harmless while nothing checked — but a pre-commit hook reads the
working tree, so on a fresh clone every file would have failed and every commit
would have been refused. A `.gitattributes` pinning the working tree to LF is
what makes Git and Prettier agree.

**`.githooks/pre-commit` checks rather than rewrites**, and `prepare` points
`core.hooksPath` at it on install so there is no new dependency and nothing to
wire up by hand.

**The Selector menu was being placed twice.** Astryx writes both a CSS anchor
position — `position-anchor`, `position-area`, `position-try-fallbacks` — and a
JS-measured `margin-block-start`, inline, on the same popover. The margin is
the fallback for browsers with no anchor positioning. Where a browser has both,
both apply: the margin moves a menu that anchor positioning has already placed.
The script picker, anchored near the bottom of the inspector, opened at the top
of the window on `margin-block-start: -391px` against an anchor at y=365.

The override in `globals.css` neutralises the margin, guarded on
`@supports (position-area: block-end)` so Safari and Firefox keep the fallback
that is still doing the whole job there.

**Astryx is pinned to an exact `0.5.0`.** 0.5.2 does not fix the positioning,
and it breaks `NumberInput`: a typed `1.25` does not take, so the line-height
field cannot be given a unitless ratio.

> Wrong, and corrected below. `NumberInput` is not broken. The line-height
> field is, on both versions, and 0.5.2 only stops hiding it.

## What was learned

**Measure which components are affected before writing the rule that fixes
them.** The obvious override was `[popover] { margin-block-start: 0 !important }`.
Measuring first showed the script Selector at `-391px`, the ratio Selector at
`-69px` — and the font Typeahead at no margin at all, landing correctly under
its field. A blanket rule would have "fixed" a component that was never broken,
and the only way to find that out was to open all three and read the numbers.

**A patch release is not automatically safe, and the suite is what says so.**
`^0.5.0` meant the lockfile was the only thing keeping 0.5.2 out. The A/B was
one production build, one machine, one dependency changed: 197/197 on 0.5.0,
196/197 on 0.5.2, and the one difference was a real user-facing break. The
existing line-height test caught it without anyone thinking to look — which is
the argument for pinning rather than trusting the range.

**`aria-expanded` is not the popover's state.** Light dismiss is the browser
closing the element directly, so React has not re-rendered and the attribute
still says expanded on the very click that shut it. Reading it produced a fix
that worked on every _other_ click — a clean alternating pattern that would
have shipped if it had not been instrumented. `:popover-open` is the real
state, and even then the component's own React state has to be settled with a
blur before its focus handler will reopen anything.

**The cheap workaround was the right one.** Swizzling the Typeahead to fix the
click behaviour would have copied 1,882 lines that style themselves with
`stylex.create`, into a workspace with no StyleX compiler — unstyled, with no
error — and the CLI's suggested Babel route disables SWC and breaks
`next/font`, which the app uses. Thirty lines in `GoogleFontPicker` did the
same job. Reading what a tool actually copies, before running it, is cheaper
than the branch that follows running it.

# Later that day — the regression was ours, and the A/B that found it was measuring nothing

Two Astryx maintainers answered the bug reports overnight. Both said the same
thing about `NumberInput`: `step` is not read on the typed path at all, they
had run the exact repro on main, on the v0.5.2 tag and on the published
tarball, and it committed `1.25` every time. One asked the question that
turned out to be the whole thing — is the test dispatching a real blur, or
asserting straight after the type?

It dispatches a blur. They were still right.

## What was done

**The repro was rebuilt from the field rather than from the theory.** Filling
`1.25` on its own commits. Filling `28`, blurring, then filling `32` does not
— it stays at 28, and a third edit takes. A plain integer is dropped exactly
the way a fraction is, so neither half of "fractional value discarded when
step is an integer" describes what happens. `step` was never involved.

**The field commits the edit before last.** `commit` runs on blur and read
`draft` and `isDirty` off the render before it. When the last keystroke
arrives in that same blur there has been no render in between, so it writes
the previous number. Logging the two callbacks showed it plainly: `onChange
from Astryx: 1.25` followed by `commit: isDirty=true draft=28`.

**Nothing looked wrong because the field shows its own draft.** The number on
screen is local state, so it reads back correctly whether or not the edit ever
reached the model. Six e2e tests asserted that number. All six passed against
a field that was writing the wrong value.

**0.5.2 does not cause this; it stops hiding it.** #5546 made a text edit one
draft that commits on blur, so `onChange` and `onBlur` became two callbacks
inside one event, where no render can happen in between. On 0.5.0 they are
separate events and the gap usually closes on its own. The bug was already
there, latent, and had been since the field was written.

**The edit moved to `line-height-edit` in `@blueprint/ui`** as pure functions,
with the component holding it in a ref as well as in state so the blur reads
what was just typed. The reset that follows the model writes state only — the
linter caught a ref being written during render, which was right, and an
effect carries it across instead.

**Select-all was clearing the field.** `a` hands the height back to auto, and
`Cmd+A` carries `key === "a"`. The shortcut swallowed the one gesture somebody
makes before replacing what is in a field. Live on 0.5.0 the whole time, and
found only because a probe used select-all to set up something else.

**Astryx is unpinned back to `^0.5.0`.** The full suite passes on 0.5.2 with
the fix — 201 tests, cold — so the range is safe. pnpm keeps the lockfile on
0.5.0 regardless, so the resolved version has not moved.

## What was learned

**A failing run is not a failing test.** The pin rested on "197/197 on 0.5.0,
196/197 on 0.5.2". Re-running it produced a 0.5.0 failure that looked like
confirmation and was `EADDRINUSE` — a dev server left over from the previous
loop, reported through the same non-zero exit. Two of the original cold-run
failures were the same thing. The A/B was one production build and one
dependency changed, which is a good design, and it still concluded the
opposite of the truth because nothing read the logs.

**Assert the far side of the change.** Every test here asked the input what it
was showing. The input shows a draft, so it is the one component in the system
that cannot answer whether an edit landed. Reading `blueprint.workspace.v1`
instead turned three green tests red immediately. A control that holds its own
state is not a witness to the model.

**A `console.log` changed the outcome, which was the actual finding.** Adding
two of them made a passing test fail on the pinned version. The instinct was
to distrust the logging. The right reading is that a test whose result moves
when you observe it is measuring a race, and the race is the bug — the same
lesson as `aria-expanded` earlier in the day, arriving by a different door.

**A test that cannot fail is worse than none.** One test written for this drove
the input and the blur in a single task to force the ordering. It passed
against the broken component, because React flushes between two separate
`dispatchEvent` calls, so it never reproduced anything. It was deleted rather
than kept as coverage. Every other assertion here was run against the old
component first and watched to fail.

**Two people were sent to look for a bug that was not there.** Both traced the
commit path, both wrote a test, both reported it passing, and one offered to
implement a fix for behaviour that already worked. The report named `step`
because `step={1}` was in the failing field, and a coincidence was filed as a
mechanism. What the report should have carried is the thing it did not have:
a repro that survives a real blur, run against the version it names.
