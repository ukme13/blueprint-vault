# 2026-09-05 — Two merge commits over the same four, and a docs app that installs what a client installs

Two pieces of work. A branch that had been merged twice and needed unpicking,
and stage 1 of the foundations plan: the docs app stops reading the studio's
tokens and starts installing the export, generated from a workspace checked
into the repository.

## What was done

**Local `main` was reconciled with the one on GitHub.** The semantic-token
branch had been merged in both places — as `6f7a163` through PR #90, and again
locally as `541ec18` — over the same four commits, so the two histories carried
the same tree by different routes. Only two commits were genuinely local: the
panel shadow and yesterday's journal. They were cherry-picked onto a branch
taken from `origin/main`, the docs branch was rebased onto that, and only then
was `main` reset. `git diff` between the rebuilt branch and the old local
`main` came back empty, which is the check that made the reset safe rather than
hopeful.

**`packages/ui/src/theme.css` no longer carries the Astryx bridge.** The bridge
is not a token: it maps Blueprint's roles onto the variable names Astryx's
components read. It was living inside a file that is the studio's own chrome,
which meant an app installing the export — a client, or the docs app — would
render every Astryx component in theme-neutral's colours. It is
`astryx-bridge.css` now, imported by `theme.css` at the position the block
occupied so the playground's cascade is unchanged, and imported directly by
anybody who installs the export.

**There is a reference workspace in the repository.** Every workspace until
today lived in somebody's localStorage, so nothing that runs without a browser
could read one. `seedWorkspaceProject` fills every slice from the studio's own
creation defaults and `apps/docs/blueprint/reference.workspace.json` is what it
writes. `emptyWorkspace` stays the other one, and the difference is the point:
it leaves both studios' slices null so a person lands on a creation screen,
while this is for the callers that need a whole system without a person. The
default track list moved into the package with it, because `PaletteStudio` held
the only copy and a script cannot reach into a component.

**The docs app builds its stylesheets from that file.** `prebuild` runs
`generate-blueprint.ts`, which reads the workspace and writes four files into
`app/blueprint`. They are committed, so a formatter change shows up as a diff
somebody reviews rather than in a client's inbox. What the files contain is
`designSystemFiles` in `@blueprint/ui` rather than a sequence of calls in the
script — which formatters run, what they are passed, and that typography ships
beside the rest rather than inside it because its unit is a decision. That rule
was about to exist twice, once in the build and once in the test that checks
the build.

**Four guards, each watched failing first.** That the committed files are what
the formatters produce today, broken by changing one hex. That the two names
the docs app paints its body with survive the export, broken by asking for one
that does not exist. That nothing under `apps/docs` imports `theme.css`, which
failed honestly before the import was switched. And a pin on the names the
bridge feeds a token from that the export does not carry, broken by taking one
off the list.

## What was learned

**The plan named the wrong file, and the app would not have said so.** It said
the docs app imports the generated CSS, meaning `blueprint.css`. The docs app
is a Tailwind app whose pages are written in `text-neutral-600` and
`bg-primary-500`, and only the `@theme` block registers those as utilities —
`blueprint.css` declares every variable and no utility. Importing it would have
left the variables resolving and every colour utility gone, which does not read
as a broken import; it reads as somebody's design change. The Tailwind file is
what this client installs. Which file is right turns out to be a fact about the
client's stack rather than about the export, which is worth knowing before
stage 5 packs an archive for somebody else's.

**Installing the export found six roles that only the studio has.** `fg.accent`,
`fg.on-action`, `action.muted`, `border.strong`, `surface.skeleton`,
`surface.track` — the bridge feeds Astryx tokens from all six, `theme.css`
defines them, and the seeded semantic layer does not, so no workspace has them
and no client can. On the running app `--color-on-accent` resolves to nothing
and the Astryx token silently keeps theme-neutral's value. Left broken: the fix
is a decision about the seed set, and adding the names to the docs app by hand
would have hidden the finding the app exists to produce. Sixteen more are the
`secondary` and `tertiary` primitive tracks, which the bridge assumes and a
studio project has never produced — that one is the bridge's fault, not the
export's.

**A test that forbids a string forbids writing down the rule.** The theme.css
guard matched `@blueprint/ui/theme.css` anywhere in a file, and the first thing
it failed on was the paragraph in `globals.css` explaining why theme.css is not
imported. It matches an import statement now. A guard on prose is a guard
against documentation.

**Prettier and a code generator will fight, and the generator loses quietly.**
`pnpm format` reformatted all four generated files the moment they existed, and
the comparison test went red — correctly, because the committed bytes were no
longer the bytes the formatters produce. Adding them to `.prettierignore` is
the fix, and the reason is worth keeping: machine output compared byte for byte
has to have exactly one writer.

**Running a script against a workspace package is not free.** `@blueprint/ui`
has a `.tsx` entry, so Node cannot load it under type stripping, and
extensionless internal imports rule out pointing at the `.ts` files. `tsx` runs
it. Inside, the package still has to be reached through `createRequire`,
because it is CommonJS and `apps/docs` is ESM, and across that edge Node guesses
named exports by lexing and cannot follow an `export *` chain — `import { x }`
fails to link, and a namespace import binds an object carrying nothing but
`default`. Three separate mechanisms, none of them visible until the script ran.

**A dependency can arrive with a decision attached.** `tsx` brings `esbuild`,
whose postinstall pnpm will not run without permission, and pnpm wrote a
placeholder into the workspace allowlist that would have failed every later
`pnpm exec`. The entry is `false`, with the reasoning written beside the two
Astryx ones already there: pnpm installs the platform package properly and
esbuild resolves the binary out of it, verified by running tsx with the script
skipped.

# Later that day — six roles that only the studio had, and a bridge asking for a palette nobody has

Stage 1 ended with a list of twenty-two names the Astryx bridge reached for
that no export defined. The list is empty now, and it emptied in two different
ways because it was two different faults wearing the same symptom.

## What was done

**Six roles joined the seed set, and the layer is twenty-five.** `fg.accent`,
`fg.on-action`, `action.muted`, `border.strong`, `surface.skeleton` and
`surface.track` had lived only in `theme.css`, which is the studio's own
chrome. Each is seeded to the primitive that chrome already resolves it to, in
both modes, so nothing in the studio moved and the docs app's eyebrow and
section rules came back through the export — with no token added by hand to the
docs app, which was the whole point of leaving them broken yesterday.

**Mirroring could not produce a single one of those pairs.** Dark has always
been seeded by mirroring the index, which is right for a role that carries the
page: text on light becomes text on dark, the same distance from its end of the
ramp. It is wrong for a role whose two values were chosen against each other.
`fg.on-action` is neutral 50 on the light fill and 950 on the dark one, and the
mirror of 50 is 900 — a shade out, and all six were. A seed role can name its
dark weight now, falling back to the mirror the way `preferWeight` falls back
to `position`.

**Two of the six are measured, four are not, and the reasons are written
down.** `fg.on-action` against `action.primary`, because it is the only
foreground in the layer whose background is not a surface and that pair is what
every filled button ships. `fg.accent` on `surface.base`, like every other
foreground. `action.muted` is kept out of the similarity grid by the rule
already there for hover and active — the same accent turned down is not a
signal beside a status badge — so it is still six signalling tokens and fifteen
pairs. `border.strong` and the two decorative surfaces carry no text and signal
nothing; they belong to the 3:1 non-text family, and deciding what each is
measured against is a question for the colour page rather than one to answer in
passing.

**A workspace file never migrated.** `readWorkspaceProject` topped a stored
layer up to the current seed set and `readWorkspaceFileProject` read the layer
and stopped, so the same document had two answers depending on which door it
came through. The docs app reads a file, which is how this surfaced at all: it
kept exporting nineteen roles while the studio had twenty-five. The file path
fills now, appending behind whatever the file chose.

**The bridge stopped assuming two tracks that have never existed.** Astryx's
cyan and purple families were fed from `secondary` and `tertiary` primitives.
Both are defined in `theme.css`; neither has ever been in a saved project,
whose six tracks are primary, neutral, success, warning, error and info. The
sixteen declarations are gone, and a test now holds the rule against
`SEED_PALETTE_TRACKS` rather than against a list of its own.

## What was learned

**A dead line and a working line look identical.** Every one of the
twenty-two was ordinary CSS pointing at a variable nothing declared, which
makes the whole declaration invalid at computed-value time — so the Astryx
token quietly keeps theme-neutral's value and no tool anywhere says a word. The
symptom is a page that looks very slightly wrong, which is indistinguishable
from a page somebody designed that way. The only thing that found them was
installing the export in an app and diffing what the bridge asks for against
what the export writes.

**The studio was showing a purple that was not purple.** `theme.css` defines
`secondary` and `tertiary` as byte-identical copies of `primary`, hue 34.49, so
a Badge asking for purple has been rendering in the brand hue — and in dark
mode as `tertiary-950`, which is near black. Removing the lines gives those
three badges theme-neutral's actual purple. It is the one visible change in the
studio, it looks better, and it is still a change: "confirm the chrome did not
move" turned into "the chrome moved in exactly one place, here is the
measurement".

**Sixty-four references remain, and they are the same bug in a quieter form.**
The status and colour-family blocks still name `success`, `warning`, `error`
and `primary` directly. They work only because the studio seeds tracks with
those names; a client who calls theirs `brand` and `grey` gets the same silent
nothing. They cannot move yet — Astryx wants four values per status where the
layer has one role — so the count is pinned by a test that lets it fall and not
rise. A ratchet is what you write when the right fix needs a decision you are
not in a position to make.

**An independent restatement of a rule is worth its maintenance.** Two tests
recompute the report's pair count from the layer with their own copy of the
exclusion list rather than calling into the package, which is deliberate: a
test that imports the rule cannot catch the rule being wrong. Both had to be
edited when `action.muted` arrived, and both failing was the system working
rather than the cost of duplication.

# Later still — an alert has four colours, and a documentation site that can show both of them

Two pieces. The status roles the bridge had been assembling out of primitives,
and stage 2 of the foundations plan: the first pages a client would read,
drawn from a workspace file.

## What was done

**Each status carries three roles beside its fill, and the layer is
thirty-seven.** `status.error` is the signal — the dot, the badge, the colour
somebody reads meaning out of — and it is not enough to build the thing the
signal goes on. An alert needs a ground, a foreground that reads on it, and a
border, and everybody was assembling those from shade numbers. Each of the
twelve takes its own status track at the weights the studio's chrome already
resolved to, verified name by name, and none of the three is a mirror of its
light value, so each names its dark weight through the mechanism the six
chrome roles needed this morning.

**The bridge went from sixty-four primitive references to eight.** Astryx
wants four values per status and four per colour family; the layer now holds
them, so the status blocks and the green, red and yellow families point at
roles. What is left is Astryx's blue family, and the reason is written beside
it: its four values are the accent's ground, edge, icon and text, and the
layer has a fill and a muted tint, neither of which is a surface to put text
on. Inventing the other two in a stylesheet the Semantics tab cannot edit is
not a fix.

**The documentation app has a dark mode, and it is the same preference the
studio has.** The state, the key, the media query and the pre-paint script
moved into @blueprint/ui as a hook. Not the provider: what surrounds it is
genuinely each application's — the studio puts a toast layer inside its Theme
and the documentation raises no toasts — so moving the whole thing would have
meant threading that config through a shared component to save fifteen lines
of JSX. The hook is the part that would otherwise drift.

**Two foundation pages, rendered from the reference workspace at build time.**
Every primitive track and shade with the variable name a developer installs;
all thirty-seven roles with both modes across, each cell naming the primitive
it resolved to; and under it the contrast rows the accessibility report
computes for this workspace, in both modes, each naming the two roles and
where they landed. Guidance comes from a TypeScript content module and names
roles, never values.

## What was learned

**Pointing the bridge at better names broke the studio, and only a measurement
said so.** The status blocks moved onto `status.success-surface` and its
neighbours, which the export now carries — and `theme.css` did not. Three
Astryx tokens per status resolved to nothing in the playground and quietly
kept theme-neutral's green. Nothing errors, nothing warns; the components just
render somebody else's colours. The docs-export guard asks whether a client's
export carries every name the bridge feeds; there is now a second guard asking
the same of the studio's own chrome, because the bridge has two audiences and
only one of them was being checked.

**What two pages share is usually smaller than it looks.** The plan said the
documentation's semantic table is the studio's, read-only. It is not: the
studio's every cell is an input, and sharing the component would have meant a
flag threading two tables through one file. What was genuinely duplicated is
three lines of rule — which group, what it is called, what order — and moving
those was the whole of the reuse. Reaching for the bigger unit would have felt
like more sharing and produced less.

**A marker that serves two purposes is worth the small component it needs.**
The guidance writes role names in backticks so a test can find them and check
them against the seed set; rendered raw, the backticks went on the page.
Stripping them from the content would have left the test with nothing to match
on, so the marker stayed and four lines of `Prose` read it. The alternative
was MDX, which the plan rules out until somebody is writing long prose, and it
still is not.

**Prose goes stale differently from data.** A table that falls behind shows a
wrong value; a paragraph that falls behind describes a token that does not
exist, and reads exactly as authoritative as the ones that do. Nothing breaks,
so nothing tells you. The test that reads role names out of the prose and
checks them against the seed set is cheap and is the only thing standing
between a rename and a page confidently explaining `action.principal`.

**The reference workspace is a fixture, and fixtures are tidier than
projects.** It stores nineteen roles, from before today; the pages show
thirty-seven because the read fills them in, which is the migration working and
also a file that has never matched what it renders. Its tracks carry no
anchors and no manual overrides, so no page has been rendered against a
palette anybody has actually tuned. And a workspace has no colour format at
all — the notation is a per-device preference in the studio, so the
documentation had to choose hex on a client's behalf, exactly as the export
generator does. If notation belongs to a system rather than to a browser, that
is a slice the file is missing, and stage 5 hands the file over.

# Later again — the Button stops naming shades, and two silent failures on the way

The last component still drawing from the primitive grid is on the layer. Six
schemes by six variants, every one of them following light and dark, and no
`--color-primary-400` left in it.

## What was done

**A tone became a pattern.** The statuses got a fill, a surface, a foreground
and a border this morning because an alert needs four colours. A button wants
those four plus a hovered fill, a pressed fill and a hovered ground — so seven
roles per tone, applied six times, and forty-eight of the layer's sixty-five
roles are now one table rather than six sets of names. The Button's scheme
block is a lookup into it.

**Three weights came back from measurement other than expected.** The border
is 450 in both modes: the canvas moves between modes and the middle of the ramp
does not, so one weight clears 3:1 on both, where the 200/800 the statuses used
for alert borders measures 1.4:1 on a light canvas and 1.06:1 on a dark one.
The label on a fill is not declared at all — `seedSemanticTokens` resolves the
fill first and takes whichever end of the neutral ramp reads better on it,
because which end that is a fact about the fill and not a preference.

**The question about yellow answered itself.** `fg.on-warning` was expected to
need a dark seed. Measured, the warning fill is `warning-450` in light, where
white reads at 4.67 and near-black at 4.18, and `warning-500` in dark, where
white reads at 5.75. Light in both, and the seed asks rather than assumes, so
a client with a paler yellow gets the other answer without anybody editing
this file.

**The bridge reached zero.** It was eighty primitive references when it was a
block inside `theme.css`, sixty-four after the status tones, eight while
Astryx's blue family had no accent surface, border or foreground to point at.
The primary tone gave it all three. Every name in that file is now a role
somebody can edit.

**`secondary` and `tertiary` are gone from the Button**, for the reason cyan
and purple left the bridge: they drew from tracks the studio's `theme.css`
defines and no saved workspace has ever contained.

## What was learned

**Tailwind's scanner reads source text, and a generated class does not exist.**
The scheme table's first version emitted
`[--btn-main:var(--color-action-primary)]` as Tailwind arbitrary-property
classes, built from the table. No complete class name appears anywhere in the
source for the scanner to find, so it generated no rule, and every button on
the documentation page rendered with no fill at all — while typechecking,
linting and passing every test. The screenshot is what caught it. The values
were `var()` references needing no compilation, so they became inline custom
properties, which is where a value that needs no build step belongs.

**`@theme` throws away tokens nothing uses, and a token file is exactly the
case where that is wrong.** The generated Tailwind export put its light values
inside `@theme` and its dark values in plain rules, so Tailwind tree-shook
every light value no utility referenced — including the whole neutral tone. In
the browser `--color-action-neutral` resolved to nothing in light and correctly
in dark, which reads as a mode bug and is a build one. `@theme static` emits
them all. A client installing a design system's token file wants the tokens,
not the subset their current markup happens to mention.

**Two guards earned their keep in one afternoon.** The Button's new
primitive scan found fifty-six shades in the old file, as designed — and then
failed on the new one, because the comment explaining what a primitive is
names one. It reads code with the comments stripped now, which is the third
time a guard here has had to learn the difference between a rule and a sentence
about a rule. And the documentation's guidance test failed the moment
`action.hover` was renamed, which is the whole reason it exists: prose goes
stale silently and reads exactly as authoritative as the paragraphs that did
not.

**A recomputation that matches is not the same as a recomputation that is
right.** The preview's issue-count test rebuilt the number from its parts and
left two terms out. It passed for months because nothing in the layer weakened
under a deficiency without failing outright first. A tone whose label sits near
its threshold broke the tie, and the formula had been wrong the whole time.

# Later again — two races, and neither was where the comment said

The keyboard-drag reorder and the export dialog have been failing intermittently
since the day each was written. Sixteen repeats of each family, measured before
anything was touched: the drag failed ten of forty-eight, the export dialog
none of ninety-six. The second number is the interesting one — the export flake
only appears in a full suite, which is why three days of running it alone had
never reproduced it.

## What was done

**The drag test was waiting for the lift, and the lift is not the signal.**
dnd-kit's `KeyboardSensor.attach()` calls `handleStart()` synchronously, which
turns `isDragging` on — and with it `aria-pressed` on the handle and the
"picked up" line in the live region — and then queues its own keydown listener
in a `setTimeout`. The timer is deliberate: it is what stops the Space that
began the drag from being read again as a movement. So every observable sign
of the lift arrives before the sensor can hear an arrow, and a key pressed in
that window is not mishandled but dropped. No listener, no event. The card
lifts and drops in the same place, which reads exactly like a reorder that does
not work.

The helper waits one turn of the task queue after seeing `aria-pressed`.
That is not a sleep and not a guess at a duration: dnd-kit queued its timer
while handling the Space, so a timer queued afterwards is queued second, and
timers of equal delay fire in registration order. Waiting for ours is waiting
for theirs to have run, and the wait ends the moment the queue reaches it.
Forty-eight of forty-eight, twice.

**The dialog button was still moving when it was clicked.** Measured on the
export dialog rather than reasoned about: with motion on, the format buttons
are still travelling 366 milliseconds after the dialog opens, about twenty-three
pixels sideways, and the helper clicks one the moment it appears. Playwright
waits for a box to hold still across two frames before clicking, and under four
workers that wait was occasionally never satisfied — a thirty-second timeout on
a click that normally takes milliseconds. Astryx honours
`prefers-reduced-motion`; under it the same button is at its final position on
the first frame and never moves at all. The suite runs with motion reduced now.

## What was learned

**A signal that arrives early is worse than no signal.** `aria-pressed` is
genuinely dnd-kit saying it has the card — the comment in the helper was right
about what it meant and wrong about what it implied. It is the correct answer
to "has the drag started" and the wrong answer to "will a key be heard", and
the two questions look identical from outside. The only place the difference is
written down is the library's own `attach()`, four lines long, and reading it
took less time than the three traces that came before.

**Slowing a test down can hide a race, which makes tracing the wrong first
move.** The instruction was to diagnose with a trace. Running the failing test
with `--trace on` passed twenty-four times out of twenty-four, and with a
single worker six out of six. Tracing costs enough per action to close the
window. The evidence that mattered was in the dependency's source and in a
count, not in a recording of a run that no longer failed.

**Reduced motion made the drag flake worse, which is how the diagnosis was
confirmed.** Applied on its own, without the queue-turn wait, the drag failed
twenty-four of forty-eight — more than twice the baseline. Removing the
animation lets the test reach the arrow key sooner, so it lands inside the
listener gap more often. A change that makes a race worse in a predictable
direction is a better confirmation of its cause than a change that makes it go
away.

**A third flake was hiding behind the first two.** With both fixed, three full
runs went 217, 216 and 217. The one failure was "Page crashed" inside the
`seededPage` fixture, before any assertion — a browser tab dying under four
workers rather than anything the suite does wrong. It has been seen twice in
about five hundred tests today. It is not either of these families, it is not
fixed here, and it is now the only thing between this suite and a reliably
green run.

# One typeface for the studio, and the docs app was in Times New Roman

The studio had no font of its own. It had three fonts and no decision behind
any of them, and the docs app had a fourth that was not a font at all.

## What was found before anything was changed

Measured on a production build, on the playground's `/`:

| Element          | Family                                                |
| ---------------- | ----------------------------------------------------- |
| A paragraph      | `Figtree, -apple-system, …` — theme-neutral's default |
| An Astryx button | `geistSans, "geistSans Fallback", sans-serif`         |
| `<body>`         | Tailwind's preflight sans stack                       |

Three typefaces on one screen. Nobody had chosen any of them: Figtree arrives
with `@astryxdesign/theme-neutral`, Geist arrives from a `.woff` file in
`app/fonts`, and the third is what Tailwind emits when nothing overrides it.

The docs app measured worse. Its `<body>` came back `"Times New Roman"`.
`globals.css` set `font-family: var(--font-geist-sans), system-ui, sans-serif`
on `:root`, and `layout.tsx` put the variable on `<body>`. A custom property
does not reach its own parent, so at `:root` the variable was undefined; an
undefined `var()` with no fallback makes the whole declaration invalid at
computed-value time, and `<html>` fell to the UA default. Every page of the
documentation has been rendering in the browser's default serif — through a
`system-ui, sans-serif` fallback list that never got the chance to apply,
because the failure was one level above it.

## What was done

**Both apps load the same three faces through `next/font/google`.** Inter for
Latin, Noto Sans Thai for Thai, Geist Mono for code. Each family gets its own
variable — next/font has no option that folds two families into one, and its
`fallback` takes plain family names rather than another loader — so the join
between them is an ordinary CSS font stack, composed once in `theme.css`:

```css
--font-sans:
  var(--font-sans-latin, Inter), var(--font-sans-thai, "Noto Sans Thai"),
  system-ui, sans-serif;
```

The class carrying those variables is on `<html>`, not `<body>`. That is the
same scope rule the docs app got wrong, and it was got wrong again here: the
first measurement after the change came back `Inter, "Noto Sans Thai",
system-ui, sans-serif` — the literal fallback names rather than next/font's
generated families — which is exactly what a declaration at `:root` resolves to
when the variables are a level below it. It looks like a working font stack.
It is a stack with both real faces missing from it.

**Geist Mono stays, from Google rather than from a file.** Keeping the mono
face means any visible change this branch makes is attributable to the sans
alone; loading it the same way as the other two leaves one mechanism and no
font binaries in the repository. Both `GeistVF.woff` and `GeistMonoVF.woff` are
gone from both apps.

**The bridge maps the three names Astryx reads.** `--font-family-body`,
`--font-family-heading` and `--font-family-code` now point at `--font-sans` and
`--font-mono`, so a page and the controls on it are drawn in one face.

## Where the Thai fallback engages

Comparing rendered widths of `สวัสดีชาวโลก` per family, after waiting for both
faces to load:

| Stack                | Width      |
| -------------------- | ---------- |
| Noto Sans Thai alone | 144.73     |
| Inter alone          | 157.25     |
| serif alone          | 157.25     |
| The studio stack     | **144.73** |

The studio stack matches Noto exactly and differs from Inter, so the Thai block
is drawn by Noto Sans Thai — per character, through the stack, with no rule
anywhere that names a script.

Two earlier attempts at this were inconclusive and both said the same thing
twice (157/157, then 153/153). They measured the width of a DOM element rather
than of the text in it, so both readings were the element's layout width and
neither could have separated the two fonts. `document.fonts.check("28px Inter",
thaiString)` is not evidence either: it returned `true`, because `check()`
accounts for system fallback and answers "can this text be drawn", not "will
this family draw it".

## The line between the studio's font and the client's

The typography studio shows both at once, inches apart: chrome in ours,
specimens in whatever the workspace names. `typography-studio-font.spec.ts`
holds that seam from both sides — the specimen must declare the workspace's own
stack and must not contain Inter, and a heading beside it must be in ours.
Pointed at `var(--font-sans)`, the specimen test fails with the regression
written into the message: expected `"Geist Sans", ui-sans-serif, system-ui`,
received the studio stack.

## Lessons

**A `var()` that resolves to its own fallback list looks like success.** Both
font bugs on this branch were the same bug — a variable declared one level
below the rule that reads it — and neither produced an error, a warning or a
blank page. One rendered Times New Roman and one rendered a plausible stack of
families that were never loaded. The tell is that the computed value contains
the fallback names _literally_; a working next/font stack contains generated
ones like `"Inter Fallback"`.

**A guard is worth what it fails on, and one of these failed on nothing.** The
test asserting that a page and its controls share a font compared a paragraph
to an Astryx button — and passed with the bridge mapping deleted, because
Astryx puts no `font-family` on this page's buttons at all. They inherit, so
they read the page's font either way. The heading is the element that carries
`var(--font-family-heading)`; measured with the mapping removed, it fell to
Figtree beside a page in Inter. The test reads a heading now, and both tests in
that describe were watched failing before the mapping went back.

## Two things the checks found that the plan did not

**The export does not carry the studio's font, and the guard said so.** Stage 1
left a test asserting that every name the Astryx bridge reaches for is one an
export defines, because a bridge line pointing at an undefined variable is
invalid at computed-value time and fails in silence. Mapping the three type
names broke it: `--font-sans` and `--font-mono` are the studio's, and an export
must not carry them — putting Inter inside a client's design system is the tool
choosing their typeface for them.

So the three type lines carry a fallback and the other forty-eight do not:

```css
--font-family-body: var(--font-sans, var(--font-family-base, sans-serif));
```

In the studio that resolves to the studio's font. In an app that installs the
export it resolves to `--font-family-base`, the client's own body font out of
their own typography export. Both readings are right where they are read.

The guard now counts bare references only, which is what it was always about:
a reference with a fallback cannot fail silently, because it resolves to the
fallback and says so in the computed value. Watched failing with one fallback
stripped, to be sure the narrowing left it teeth.

**The docs app could not import the token, so it got its own file.** The first
build after the mapping measured the playground in Inter and the docs app in
`-apple-system, BlinkMacSystemFont, "Segoe UI", …` — Tailwind's default, which
defines `--font-sans` itself, so our `var()` found a value and never reached
its fallback. The docs app installs the export and is forbidden from importing
`theme.css`, which is where the token was.

That prohibition is about colour. The docs app is the tool's own documentation
and its chrome is the tool's chrome; it is only the _export_ it has to consume
like a client. So the two type tokens moved out of `theme.css` into
`studio-font.css` — a file that carries nothing else, is imported by both apps,
and is in no export. Written once, read in two places, and the guard that keeps
the docs app off the studio's colours is untouched.

Measured after: both apps' `--font-sans`, `--font-family-body`,
`--font-family-heading` and every element sampled on either home page come back
`"Inter", "Inter Fallback", "Noto Sans Thai", "Noto Sans Thai Fallback",
system-ui, sans-serif`, and both code roles come back Geist Mono.

# `@theme` without `static`, and the role that was never there

Reported: the "Add font" button on `/typography` has no hover or pressed
colour, because `--color-action-primary-hover` is missing from the compiled
CSS — eleven roles in total, dropped by Tailwind's tree-shaking of `@theme`.

The diagnosis was right and the details were not, in a way worth writing down.

## What the page actually measured

`--color-action-primary-hover` is present. Some utility class names it as text,
so the scanner kept it. **Hover works.** What is missing is
`--color-action-primary-active`, and the state that breaks is _pressed_:

|             | light                     | dark                      |
| ----------- | ------------------------- | ------------------------- |
| rest        | `oklch(0.5 0.157 34.49)`  | `oklch(0.6 0.189 34.49)`  |
| hover       | `oklch(0.45 0.141 34.49)` | `oklch(0.65 0.205 34.49)` |
| **pressed** | **`rgba(0, 0, 0, 0)`**    | **`rgba(0, 0, 0, 0)`**    |

And it is not eleven roles, it is **twenty-eight**: `action.primary-active` and
`-surface-hover`, the whole `action.neutral` tone, every `fg.on-*` but
`fg.on-action`, `border.muted`, `action.secondary`, and hover/active/
surface-hover for all four statuses. A role survives only where some utility
class happens to name it too, which is why the wreckage looks like an arbitrary
handful rather than a rule.

After `@theme static`, pressed resolves in both modes —
`oklch(0.4 0.126 34.49)` on light, `oklch(0.6803 0.1865 34.49)` on dark.

## The twenty-eighth

`@theme static` restored twenty-seven. `--color-action-secondary` stayed empty,
because it is not in `theme.css` at all — it has been in the seed set since the
tone pattern landed and was never written into the studio's own chrome.

That is the part worth keeping. **A role the stylesheet omits and a role
Tailwind tree-shakes are indistinguishable from the page**: both resolve to the
empty string, both take their declaration out at computed-value time, and
neither says anything. One bug hid the other, and fixing the first is what
surfaced the second. The `secondary` primitives were already in the file —
twenty shades of them, with nothing reading a single one.

## The docs app is clean, and was already

All three `@theme` blocks in its generated `blueprint.tailwind.css` carry
`static` — that is the 2026-09-05 export fix — its `globals.css` declares no
`@theme` of its own, and every generator in `packages/ui` emits `@theme static`
already. Measured rather than grepped: all 266 declared variables resolve in
both modes on `/` and on `/foundations/semantic`. Nothing to fix.

## The test, and what it could not import

The instruction was to build the role list from `seedSemanticTokens` rather
than write it out. The e2e loader cannot import it: the package entry is a
`.tsx` that pulls in React and Astryx, and its `export *` barrels come back
holding only `__esModule` and `default` through Playwright's transform. Adding
a React-free `./color` entry point to the package did not change that.

So the list comes from the export the studio itself produces — downloaded in
the test, with every alias line read out of it. That is the same seeded layer
by another route, it grows when the seed set grows, and it asks a better
question than the import would have: _everything the studio is willing to hand
a client, it has to be able to draw itself._

## Lessons

**The empty string is this codebase's null pointer.** Three separate faults
this session ended at the same place — an undefined custom property, a
declaration invalid at computed-value time, and no error. A font that fell to
Times New Roman, a `var()` that resolved to its own literal fallbacks, and now
a button with no pressed colour. None of them failed loudly; all three were
found by measuring a computed value and none by reading the code.

**A bug report is a measurement, not a diagnosis.** "Hover goes transparent,
eleven roles, `--color-action-primary-hover`" pointed at exactly the right
file and the right one-word fix, and named the wrong state, the wrong
variable, and less than half the damage. Reproducing it before believing it
cost one run and turned up a role nobody had noticed was missing.
