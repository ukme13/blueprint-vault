# 2026-09-05 — Two merge commits over the same four, and a docs app that installs what a client installs

Two pieces of work. A branch that had been merged twice and needed unpicking,
and stage 1 of the foundations plan: the docs app stops reading the studio's
tokens and starts installing the export, generated from a workspace checked
into the repository.

## What was done

**Local `main` was reconciled with the one on GitHub.** The semantic-token
branch had been merged in both places — as `6f7a163` through PR #90, and again
locally as `541ec18` — over the same four commits, so the two histories carried
the same tree by different routes. Only two commits were genuinely local: the
panel shadow and yesterday's journal. They were cherry-picked onto a branch
taken from `origin/main`, the docs branch was rebased onto that, and only then
was `main` reset. `git diff` between the rebuilt branch and the old local
`main` came back empty, which is the check that made the reset safe rather than
hopeful.

**`packages/ui/src/theme.css` no longer carries the Astryx bridge.** The bridge
is not a token: it maps Blueprint's roles onto the variable names Astryx's
components read. It was living inside a file that is the studio's own chrome,
which meant an app installing the export — a client, or the docs app — would
render every Astryx component in theme-neutral's colours. It is
`astryx-bridge.css` now, imported by `theme.css` at the position the block
occupied so the playground's cascade is unchanged, and imported directly by
anybody who installs the export.

**There is a reference workspace in the repository.** Every workspace until
today lived in somebody's localStorage, so nothing that runs without a browser
could read one. `seedWorkspaceProject` fills every slice from the studio's own
creation defaults and `apps/docs/blueprint/reference.workspace.json` is what it
writes. `emptyWorkspace` stays the other one, and the difference is the point:
it leaves both studios' slices null so a person lands on a creation screen,
while this is for the callers that need a whole system without a person. The
default track list moved into the package with it, because `PaletteStudio` held
the only copy and a script cannot reach into a component.

**The docs app builds its stylesheets from that file.** `prebuild` runs
`generate-blueprint.ts`, which reads the workspace and writes four files into
`app/blueprint`. They are committed, so a formatter change shows up as a diff
somebody reviews rather than in a client's inbox. What the files contain is
`designSystemFiles` in `@blueprint/ui` rather than a sequence of calls in the
script — which formatters run, what they are passed, and that typography ships
beside the rest rather than inside it because its unit is a decision. That rule
was about to exist twice, once in the build and once in the test that checks
the build.

**Four guards, each watched failing first.** That the committed files are what
the formatters produce today, broken by changing one hex. That the two names
the docs app paints its body with survive the export, broken by asking for one
that does not exist. That nothing under `apps/docs` imports `theme.css`, which
failed honestly before the import was switched. And a pin on the names the
bridge feeds a token from that the export does not carry, broken by taking one
off the list.

## What was learned

**The plan named the wrong file, and the app would not have said so.** It said
the docs app imports the generated CSS, meaning `blueprint.css`. The docs app
is a Tailwind app whose pages are written in `text-neutral-600` and
`bg-primary-500`, and only the `@theme` block registers those as utilities —
`blueprint.css` declares every variable and no utility. Importing it would have
left the variables resolving and every colour utility gone, which does not read
as a broken import; it reads as somebody's design change. The Tailwind file is
what this client installs. Which file is right turns out to be a fact about the
client's stack rather than about the export, which is worth knowing before
stage 5 packs an archive for somebody else's.

**Installing the export found six roles that only the studio has.** `fg.accent`,
`fg.on-action`, `action.muted`, `border.strong`, `surface.skeleton`,
`surface.track` — the bridge feeds Astryx tokens from all six, `theme.css`
defines them, and the seeded semantic layer does not, so no workspace has them
and no client can. On the running app `--color-on-accent` resolves to nothing
and the Astryx token silently keeps theme-neutral's value. Left broken: the fix
is a decision about the seed set, and adding the names to the docs app by hand
would have hidden the finding the app exists to produce. Sixteen more are the
`secondary` and `tertiary` primitive tracks, which the bridge assumes and a
studio project has never produced — that one is the bridge's fault, not the
export's.

**A test that forbids a string forbids writing down the rule.** The theme.css
guard matched `@blueprint/ui/theme.css` anywhere in a file, and the first thing
it failed on was the paragraph in `globals.css` explaining why theme.css is not
imported. It matches an import statement now. A guard on prose is a guard
against documentation.

**Prettier and a code generator will fight, and the generator loses quietly.**
`pnpm format` reformatted all four generated files the moment they existed, and
the comparison test went red — correctly, because the committed bytes were no
longer the bytes the formatters produce. Adding them to `.prettierignore` is
the fix, and the reason is worth keeping: machine output compared byte for byte
has to have exactly one writer.

**Running a script against a workspace package is not free.** `@blueprint/ui`
has a `.tsx` entry, so Node cannot load it under type stripping, and
extensionless internal imports rule out pointing at the `.ts` files. `tsx` runs
it. Inside, the package still has to be reached through `createRequire`,
because it is CommonJS and `apps/docs` is ESM, and across that edge Node guesses
named exports by lexing and cannot follow an `export *` chain — `import { x }`
fails to link, and a namespace import binds an object carrying nothing but
`default`. Three separate mechanisms, none of them visible until the script ran.

**A dependency can arrive with a decision attached.** `tsx` brings `esbuild`,
whose postinstall pnpm will not run without permission, and pnpm wrote a
placeholder into the workspace allowlist that would have failed every later
`pnpm exec`. The entry is `false`, with the reasoning written beside the two
Astryx ones already there: pnpm installs the platform package properly and
esbuild resolves the binary out of it, verified by running tsx with the script
skipped.
